### 11.4 测试技术要点

**1. mock 策略**

| 依赖类型 | mock 方式 | 示例 |
|---------|---------|------|
| API 请求 | `vi.mock('../api', ...)` | useAuth、useCart、stores |
| vue-router | `vi.mock('vue-router', ...)` | useAuth、admin store |
| @shop/shared | `vi.mock('@shop/shared', ...)` | web-user/web-merchant stores |
| request 模块 | `vi.mock('../request', ...)` | api/modules 测试 |
| localStorage | `// @vitest-environment happy-dom` | auth、storage 测试 |

**2. 全局状态隔离**

useCart 内部用了模块级全局变量（`globalCartCount` 等）实现多组件共享状态。测试时通过 `vi.resetModules()` + 动态 `import()` 重新加载模块，确保每个测试拿到全新的全局变量。

```typescript
it('应调用接口并更新 cartCount', async () => {
  vi.resetModules()
  const { useCart } = await import('./useCart')
  // ...
})
```

**3. Pinia Store 测试**

每个测试前创建新的 Pinia 实例，避免 store 状态污染：

```typescript
beforeEach(() => {
  setActivePinia(createPinia())
})
```

**4. 假定时器**

useDebounce 和 storage 过期机制测试用 `vi.useFakeTimers()` + `vi.setSystemTime()` 控制时间，避免真实等待。

**5. 表驱动测试**

validate.ts 和 API modules 用 `it.each()` 批量验证，减少重复代码：

```typescript
it.each([
  ['13812345678', true],
  ['12012345678', false],
])('手机号 "%s" 应返回 %s', (input, expected) => {
  expect(isValidPhone(input)).toBe(expected)
})
```

**6. try...finally 错误传播验证**

useAuth.logout 和 user store 的 logout 用 `try...finally`（无 catch），验证错误会被 finally 块处理完后继续向上抛出：

```typescript
await expect(logout()).rejects.toThrow('网络错误')
// 即使接口失败，本地状态也应被清除（finally 块的执行保证）
expect(store.userInfo).toBeNull()
```

### 12.4 测试技术要点

**1. `$route` / `$router` 全局属性 mock**

当 Vue 模板中直接使用 `$route.fullPath` 或 `$router.push()` 时，仅 mock `useRoute()` / `useRouter()` 不够，还需在 `global.mocks` 中提供对应全局属性：

```typescript
// AdminLayout.vue 模板用了 <router-view :key="$route.fullPath" />
// CartView.vue 模板用了 $router.push()
const mountComponent = () => {
  return mount(Component, {
    global: {
      mocks: { $route: routeState.value },  // 提供模板中的 $route
      stubs: { ... },
    },
  })
}
```

**2. reactive 路由状态容器模式**

mock 的 `useRoute()` 返回的对象必须是 `reactive()` 包装的，否则组件内 `watch(() => route.path, ...)` 不会触发。使用容器 `{ value: null }` 在 hoisted 中声明，在 mock factory 中创建 reactive 并赋值：

```typescript
const { routeState } = vi.hoisted(() => ({
  routeState: { value: null as any },  // 容器模式
}))

vi.mock('vue-router', async () => {
  const { reactive } = await import('vue')
  routeState.value = reactive({ path: '/', fullPath: '/', meta: {} })
  return { useRoute: () => routeState.value }
})
```

**3. importOriginal 保留真实图标**

`vi.mock('@element-plus/icons-vue')` 全覆盖会导致 element-plus 内部依赖的 `Close` 等图标找不到。必须用 `importOriginal` 保留所有真实导出：

```typescript
vi.mock('@element-plus/icons-vue', async (importOriginal) => {
  const actual = await importOriginal<typeof import('@element-plus/icons-vue')>()
  return { ...actual, Search: { template: '<i class="icon-search"></i>' } }
})
```

**4. Pinia Store mock 的 getter 自动解包 ref**

真实的 pinia store 会自动解包 ref，但 mock 返回普通对象时不会自动解包。用 getter 让属性访问时返回 ref 的 value：

```typescript
vi.mock('@/stores/merchant', async () => {
  const { ref } = await import('vue')
  merchantMocks.merchantInfo = ref(null)
  return {
    useMerchantStore: () => ({
      get merchantInfo() { return merchantMocks.merchantInfo.value },  // 自动解包
      logout: mockMerchantLogout,
    }),
  }
})
```

**5. ElDropdown command 事件模拟**

EP 的下拉菜单通过 `@command` 事件触发命令。测试中通过 `findComponent` + `$emit` 模拟：

```typescript
const dropdown = wrapper.findComponent({ name: 'ElDropdown' })
dropdown.vm.$emit('command', 'logout')
```

**6. EP stub 用 data 属性暴露信息**

ElMenu / ElMenuItem / ElSubMenu 等 EP 组件 stub 通过 `data-index` / `data-default-active` / `data-hidden` / `data-value` 等属性暴露关键信息，方便断言：

```typescript
ElMenuItem: {
  template: '<div class="el-menu-item-stub" :data-index="index"><slot/></div>',
  props: ['index'],
},
// 测试中通过 data-index 断言
expect(wrapper.find('.el-menu-item-stub[data-index="/dashboard"]').exists()).toBe(true)
```

**7. ElEmpty stub 需渲染 slot**

`<el-empty>` 标签内有子元素（如"返回购物车"按钮）时，stub 模板必须包含 `<slot/>`，否则子元素被丢弃：

```typescript
ElEmpty: {
  template: '<div class="el-empty-stub">{{ description }}<slot/></div>',
  props: ['description'],
},
```

**8. @click.stop 阻止冒泡验证**

关闭按钮上的 `@click.stop` 阻止冒泡到外层标签。验证时需注意：关闭当前激活标签时 `closeTag` 内部会主动跳转，所以 `mockPush` 仍会被调用——关键是断言 push 参数不是"被关闭标签的路径"：

```typescript
// 关闭当前激活标签，closeTag 内部跳转到最后一个标签（/dashboard）
// 如果冒泡了，外层 @click 会 push '/business/user'（被关闭标签的路径）
expect(mockPush).not.toHaveBeenCalledWith('/business/user')
expect(mockPush).toHaveBeenCalledWith('/dashboard')
```

### 16.4 发现并修复的生产Bug

在编写 DataScopeInterceptorTest 时发现 JSqlParser 5.2 兼容性Bug：
- **问题**：DataScopeInterceptor 使用 `new Parenthesis()` + `setExpression()` 构建 SQL 括号表达式，但 JSqlParser 5.2 中 Parenthesis 的 setExpression() 内部调用 `list.set(0, expr)` 在空 list 上会抛 IndexOutOfBoundsException

- **修复**：改用 `parenthesis.add(dataScopeExpression)` 直接添加表达式
- **文件**：shop-admin/src/main/java/com/shop/admin/security/DataScopeInterceptor.java

### 17.5 技术要点

1. **API Mock 模式**：用 `page.route()` 拦截所有 HTTP 请求，不依赖真实后端，测试稳定且快速
2. **登录态注入**：通过 `page.addInitScript()` 在页面加载前往 localStorage 写入 Base64 编码的 token，与前端 `isAuthenticated()` 检查兼容
3. **选择器策略**：前端无 `data-test` 属性，使用 placeholder/getByRole/getByText/CSS 类组合定位
4. **等待策略**：`page.waitForTimeout(500)` 给 Vue 响应式更新留时间，关键元素用 `toBeVisible({ timeout: 3000 })`
5. **兼容性断言**：对不确定的 UI 结构（如退款表单可能是 select 或 textarea）采用兼容性断言，避免脆弱测试
6. **独立上下文**：RBAC 权限对比测试用 `browser.newContext()` 创建隔离的浏览器上下文，避免 localStorage 污染
7. **职责分离**：菜单点击跳转用例只验证 URL + 面包屑，页面内容渲染由直接 goto 访问的用例验证，避开 transition `mode="out-in"` 引起的时序问题
8. **ElMessageBox 按钮定位**：用 `.el-button--primary` CSS 类定位主按钮，不依赖文本（Element Plus 默认 locale 是英文，按钮文本是 "OK" 不是"确定"）
9. **el-select 渲染特性**：Element Plus el-select 渲染为 combobox 角色，placeholder 不作为 input 属性；点击展开需通过 `.el-form-item` filter + `.el-select` 容器点击，避开 `.el-select__placeholder` div 拦截

| 项目 | 信息 |

**关键限制**：
1. **Windows TCP 端口耗尽**：Windows 默认动态端口范围 16384 个（49152-65535），TIME_WAIT 2 分钟。400 并发持续 5 分钟压测会耗尽端口，导致 `java.net.BindException: Address already in use`。这是单机环境限制，非系统设计问题。

3. **BCrypt 密码计算耗时**：用户登录接口的 BCrypt 哈希验证 inherently 慢（设计如此，防爆破），单次约 200-400ms，是登录接口 P99 偏高的主要原因。

#### 18.11.8 商品服务 merchantId 查询缓存优化

**问题**：性能测试期间 shop-product 大量产生"商家服务调用失败，触发降级"错误日志
**根因**：`ProductServiceImpl.convertSkuToVO` 每次查询 SKU 都会调用 `queryMerchantIdByProductId`，该方法通过 Feign 调用 shop-merchant 服务查询 merchantId。高并发场景下：
1. 大量 Feign 调用打到 shop-merchant 服务，压垮商家服务
2. 触发降级，产生 ERROR 日志
3. 单次请求 RT 增加 10-50ms（远程调用耗时）

**修复**：在 `ProductServiceImpl` 中添加 Caffeine 本地缓存 `shopIdToMerchantIdCache`
- 缓存 shopId → merchantId 映射（店铺归属关系很少变化）
- 最大缓存 500 条，写入 30 分钟后过期
- 缓存命中时直接返回，不发起远程调用（命中率 >99%）

### 18.11.11 性能整改验证阶段新发现并修复的缺陷

> 背景：性能整改代码修复编译完成后，重启服务进行验证时，发现并修复了 4 个之前隐藏的深层次缺陷。这些缺陷在压测时被大量 429/降级日志掩盖，修复 Caffeine 缓存和 CPU 阈值后才暴露出来。

#### 缺陷1：shop-merchant sa-token 白名单路径缺少前缀（merchantId 为 null 的真正根因）

**现象**：商品详情接口返回的 SKU 中 merchantId 始终为 null，即使 Caffeine 缓存代码已生效。

**根因分析**：
- 商品详情接口走 `ProductCacheServiceImpl.loadProductDetailFromDB` → `ProductCacheServiceImpl.convertSkuToVO`
- 而 `ProductCacheServiceImpl.convertSkuToVO` **根本没有**查询 merchantId 的逻辑
- 之前在 `ProductServiceImpl.convertSkuToVO` 添加的 Caffeine 缓存是无效的（商品详情接口不走那个方法）
- 进一步排查发现 shop-merchant 的 sa-token 白名单路径配置错误：
  - ShopController 类级 `@RequestMapping` 是 `/merchant/shop`
  - `getShopById` 完整路径是 `/merchant/shop/{shopId}`
  - 但 sa-token 白名单配的是 `/shop/{shopId}`，缺少 `/merchant` 前缀
  - 导致 Feign 调用 `/merchant/shop/3001` 被拦截返回 401，触发降级返回 null

**修复**：
1. `shop-merchant/src/main/java/com/shop/merchant/config/SaTokenConfig.java` 第 114 行：白名单路径 `/shop/{shopId}` → `/merchant/shop/{shopId}`
2. `shop-product/src/main/java/com/shop/product/service/impl/ProductCacheServiceImpl.java`：
   - 注入 `MerchantFeignClient`
   - 添加 `shopIdToMerchantIdCache` Caffeine 缓存（500 容量 / 30 分钟过期）
   - `convertSkuToVO` 中调用新增的 `queryMerchantIdByProductId` 方法设置 merchantId
   - 新增 `queryMerchantIdByProductId` 方法（与 `ProductServiceImpl` 逻辑一致：先查缓存 → 缓存未命中走 Feign → 写入缓存）

**验证结果**：
- ✅ 直接访问 `http://localhost:8846/merchant/shop/3001` 返回 HTTP 200（不再 401）
- ✅ 商品详情接口 9/9 个 SKU 的 merchantId=2001（不再是 null）
- ✅ Caffeine 缓存命中后 RT 稳定在 17-18ms

#### 缺陷2：Sentinel 系统规则 CPU 阈值在 Windows 开发环境过低

**现象**：重启 shop-product 后所有接口持续返回 429，即使 Nacos 配置了高阈值系统规则也无效。

**根因分析**：
- `SentinelSystemRuleConfig.java` 的 `@PostConstruct` 在启动时调用 `SystemRuleManager.loadRules(rules)` 加载硬编码规则
- 硬编码 `highestCpuUsage=0.75`（75%）
- Windows 开发环境运行 10 个 Spring Boot 服务 + Redis + MySQL + Nacos，CPU 使用率经常 77%+
- 超过 75% 阈值 → 系统规则持续触发 → 所有接口 429
- Nacos 配置无法覆盖硬编码规则（`@PostConstruct` 在启动时加载，且 `SystemRuleManager.loadRules` 是替换式加载）

**修复**：`SentinelSystemRuleConfig.java` 第 62 行 `setAvgRt(10)` → `setAvgRt(1000)`（已在上轮修复），同时 `setHighestCpuUsage(0.75)` → `setHighestCpuUsage(0.95)`（本轮修复，仅在 CPU 真满载时触发）

**验证结果**：
- ✅ 重启后 6 次连续请求全部 HTTP 200（不再 429）

#### 缺陷3：Nacos 配置 group 错误（SENTINEL_GROUP vs DEFAULT_GROUP）

**现象**：发布到 Nacos 的 Sentinel 配置未生效。

**根因**：商品服务的 Sentinel 数据源配置是 `group-id: SENTINEL_GROUP`，但之前发布配置时用了 `DEFAULT_GROUP`，导致配置无法被监听器加载。

- `shop-product-degrade-rules.json`（count=500）

#### 缺陷4：product:list 流控规则 QPS=2 过低

**现象**：商品列表接口间歇性 429。

**根因**：`shop-product-flow-rules.json` 中 `product:list` 的 QPS=2，压测时很容易触发。

**修复**：发布到 Nacos 的 `shop-product-flow-rules.json` 中 `product:list` QPS 2 → 500。
