# Shop 项目测试方案

> 适用版本：Spring Boot 4.0.0 / Spring Cloud 2025.1.0 / Vue 3.5 / Java 21
> 文档目的：为 Shop 电商项目（11 个后端微服务 + 3 个前端子系统）制定一套主流、可落地的全栈测试方案，覆盖从单元测试到端到端测试的完整测试金字塔。

---

## 一、概述

### 1.1 项目背景

Shop 是一个微服务电商系统，包含：

- **后端**：11 个 Spring Boot 微服务（gateway / user / merchant / product / cart / order / payment / admin / marketing / seckill / common + model）
- **前端**：3 个 Vue 3 子系统（web-user 消费者端、web-merchant 商家端、web-admin 管理端）+ 1 个 shared 共享包
- **中间件**：MySQL、Redis、Nacos、RocketMQ、Elasticsearch、Sentinel、MinIO、Seata

业务核心链路涉及**高并发秒杀、分布式事务、幂等性、限流熔断**等复杂场景，测试至关重要。

### 1.2 测试目标

| 目标 | 说明 |
|------|------|
| 功能正确性 | 保证核心业务流程（注册登录、商品浏览、下单支付、秒杀、评价）功能正确 |
| 高可用性 | 验证限流、熔断、降级、幂等等高可用机制生效 |
| 性能达标 | 核心接口 P99 < 500ms，秒杀接口支持 2000 QPS |
| 回归效率 | 自动化测试覆盖核心场景，防止迭代引入回归 |
| 质量可视 | 覆盖率与测试报告可量化、可追踪 |

### 1.3 适用范围

- 后端：shop-common / shop-model / shop-user / shop-merchant / shop-product / shop-cart / shop-order / shop-payment / shop-admin / shop-marketing / shop-seckill / shop-gateway
- 前端：@shop/shared / web-user / web-merchant / web-admin

### 2.1 后端现状

## 三、测试分层架构（测试金字塔）

采用业界主流的**测试金字塔**模型，从底到顶分层：

```
            ┌─────────────────────┐
            │   E2E 端到端测试     │  ← 少量，验证完整业务链路（Playwright）
            │     (Playwright)    │
            ├─────────────────────┤
            │   集成测试 / 契约测试  │  ← 中等，验证模块间协作（Testcontainers）
            │  (Testcontainers)   │
            ├─────────────────────┤
            │   切片测试           │  ← 中等，验证 Controller/DAO 层
            │ (@WebMvcTest/DAO)   │
            ├─────────────────────┤
            │   单元测试           │  ← 大量，验证业务逻辑（JUnit5+Mockito）
            │ (JUnit5+Mockito)    │
            └─────────────────────┘
```

**比例建议**：单元测试 70% / 切片+集成测试 20% / E2E 测试 10%

### 3.1 各层职责定义

| 层级 | 后端 | 前端 | 执行速度 | 反馈粒度 |
|------|------|------|---------|---------|
| 单元测试 | Service/Util/Aspect 纯逻辑 | 工具函数/composable 单函数 | 毫秒级 | 精确到函数 |
| 切片测试 | Controller 层（@WebMvcTest）、DAO 层（@MybatisPlusTest + H2） | 组件测试（@vue/test-utils） | 秒级 | 精确到层 |
| 集成测试 | 全栈启动 + Testcontainers 真实中间件 | 组件交互 + Mock API | 秒级 | 模块级 |
| 契约测试 | Spring Cloud Contract（Provider 端） | Consumer 端契约验证 | 秒级 | 接口级 |
| E2E 测试 | - | Playwright 模拟真实用户操作 | 分钟级 | 业务流程级 |

## 四、后端测试方案

### 4.1 单元测试（已有，持续完善）

#### 4.1.1 技术栈

- **JUnit 5**（Jupiter）：测试框架
- **Mockito**：Mock 依赖
- **AssertJ**：流式断言（比原生断言更可读）
- **reactor-test**：gateway 响应式测试

#### 4.1.2 规范（沿用现有规范）

```java
/**
 * 用户服务测试
 * 小白理解：这个类专门测试 UserServiceImpl 里的每个方法，比如注册、登录
 */
@DisplayName("用户服务 UserServiceImpl 单元测试")
@ExtendWith(MockitoExtension.class)
class UserServiceImplTest {

    @Mock
    private UserMapper userMapper;       // 模拟数据库操作，不真实连库

    @InjectMocks
    private UserServiceImpl userService; // 被测对象，Mock 会自动注入

    @Nested
    @DisplayName("注册功能")
    class RegisterTest {
        
        @Test
        @DisplayName("注册成功：手机号不存在时返回用户ID")
        void register_phoneNotExists_returnsUserId() {
            // 场景：手机号没被注册过
            // 验证：返回新增的用户ID
        }
    }
}
```

**命名规则**：`被测方法_场景_预期结果`（三段式下划线分隔）

**断言风格**：统一使用 AssertJ

```java
// 推荐：AssertJ 流式断言，错误信息更友好
assertThat(result.getCode()).isEqualTo(200);
assertThatThrownBy(() -> service.login(dto))
    .isInstanceOf(BusinessException.class)
    .hasFieldOrPropertyWithValue("code", ErrorCode.USER_NOT_FOUND.getCode());
```

### 4.2 切片测试（新增）

切片测试只加载某一层的组件，比全栈集成测试快，比单元测试真实。

#### 4.2.1 Controller 切片测试（@WebMvcTest）

**依赖**：无需新增，`spring-boot-starter-test` 已包含。

**用途**：验证 Controller 的请求路由、参数校验、异常处理、响应格式，不加载 Service。

```java
/**
 * 订单 Controller 切片测试
 * 小白理解：只测 Controller 层，Service 用 Mock 假数据，不连数据库
 */
@WebMvcTest(OrderController.class)
@Import(GlobalExceptionHandler.class) // 导入全局异常处理，验证异常响应
@DisplayName("订单 Controller 切片测试")
class OrderControllerTest {

    @Autowired
    private MockMvc mockMvc;  // 模拟 HTTP 请求，不用真启动 Tomcat

    @MockBean
    private OrderService orderService; // Service 用 Mock，不真实执行

    @Test
    @DisplayName("创建订单：参数校验失败时返回 400")
    void createOrder_invalidParam_returns400() throws Exception {
        // 场景：请求体缺少必填字段
        // 验证：返回 400 状态码和错误信息
        mockMvc.perform(post("/api/order/create")
                .header("X-Idempotent-Key", "test-key-001")
                .contentType(MediaType.APPLICATION_JSON)
                .content("{}"))  // 空请求体
            .andExpect(status().isBadRequest())
            .andExpect(jsonPath("$.code").value(400));
    }
}
```

**适用模块**：所有业务的 Controller 层。

#### 4.2.2 DAO 层切片测试（MyBatis-Plus + H2）

**需新增依赖**（根 pom.xml）：

```xml
<!-- H2 内存数据库，用于 DAO 测试，不连真实 MySQL -->
<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>test</scope>
</dependency>
```

**用途**：验证 Mapper 的 SQL 语句、复杂查询、分页，使用 H2 内存库避免污染真实数据。

```java
/**
 * 订单 Mapper 测试
 * 小白理解：用 H2 内存数据库测试 SQL 写得对不对，测试完自动销毁
 */
@SpringBootTest
@ActiveProfiles("test")  // 使用 test 配置，指向 H2
@DisplayName("订单 Mapper 集成测试")
class OrderInfoMapperTest {

    @Autowired
    private OrderInfoMapper orderInfoMapper;

    @Test
    @DisplayName("根据用户ID分页查询订单")
    void selectPageByUserId_returnsPagedOrders() {
        // 场景：构造 3 条订单数据
        // 验证：分页查询返回正确数量和顺序
    }
}
```

> ⚠️ 注意：H2 与 MySQL 的 SQL 方言有差异，复杂 SQL（如 `ON DUPLICATE KEY UPDATE`）可能不兼容。对于强依赖 MySQL 特性的 SQL，建议用 Testcontainers（见 4.3）。

### 4.3 集成测试（新增，Testcontainers）

集成测试启动完整 Spring 上下文，使用 **Testcontainers** 启动真实的 MySQL/Redis/RocketMQ 容器，验证模块间协作。

#### 4.3.1 新增依赖

```xml
<!-- Testcontainers 核心依赖，用于集成测试启动真实中间件容器 -->
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>testcontainers</artifactId>
    <version>1.20.4</version>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>mysql</artifactId>
    <version>1.20.4</version>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>1.20.4</version>
    <scope>test</scope>
</dependency>
```

> 前置条件：本机需安装 Docker（Windows 用 Docker Desktop）。

#### 4.3.2 使用示例

```java

        .withInitScript("sql/init-order-schema.sql");

    @Autowired

    @Test
    @DisplayName("完整下单流程：扣库存 → 扣优惠券 → 创建订单")
    void createOrder_fullFlow_success() {
        // 场景：构造商品、优惠券、地址数据
        // 验证：订单创建成功，库存扣减，优惠券状态变更
    }
}
```

**适用场景**：
- 订单全链路（下单 → 支付 → 发货 → 收货 → 评价）
- 秒杀全链路（预热 → 抢购 → 异步下单 → 库存回滚）
- 限流全链路（Redis Lua 滑动窗口 → 黑名单 → 降级）
- 分布式事务（Seata 扣库存回滚）

### 4.4 契约测试（Spring Cloud Contract）

微服务间通过 Feign 调用，Provider（提供方）接口变更容易导致 Consumer（消费方）报错。契约测试用**契约文件**锁定接口约定。

#### 4.4.1 适用场景

| Provider | Consumer | 接口 |
|----------|----------|------|
| shop-product | shop-order | 扣减库存 |
| shop-product | shop-user | 商品浏览足迹 |
| shop-order | shop-product | 增加销量 |
| shop-coupon | shop-order | 优惠券核销 |
| shop-user | shop-product | 用户信息查询 |

#### 4.4.2 实现思路

1. Provider 端编写契约（Groovy DSL）
2. 插件自动生成 Consumer 端的 Mock stub
3. Provider 端运行契约验证测试，确保实现符合契约

> 详见 [Spring Cloud Contract 官方文档](https://docs.spring.io/spring-cloud-contract/docs/current/reference/html/)

### 4.5 覆盖率工具（新增，JaCoCo）

#### 4.5.1 新增插件（根 pom.xml）

```xml
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>0.8.12</version>
    <executions>
        <execution>
            <goals><goal>prepare-agent</goal></goals>
        </execution>
        <execution>
            <id>report</id>
            <phase>test</phase>
            <goals><goal>report</goal></goals>
        </execution>
        <execution>
            <id>check</id>
            <goals><goal>check</goal></goals>
            <configuration>
                <rules>
                    <rule>
                        <element>BUNDLE</element>
                        <limits>
                            <limit>
                                <counter>LINE</counter>
                                <value>COVEREDRATIO</value>
                                <minimum>0.60</minimum>  <!-- 行覆盖率不低于 60% -->
                            </limit>
                        </limits>
                    </rule>
                </rules>
            </configuration>
        </execution>
    </executions>
</plugin>
```

#### 4.5.2 覆盖率目标

| 模块 | 行覆盖率目标 | 分支覆盖率目标 |
|------|------------|-------------|
| shop-common | 80% | 70% |
| shop-order | 70% | 60% |
| shop-seckill | 75% | 65% |
| shop-payment | 70% | 60% |
| 其他业务模块 | 60% | 50% |

## 五、前端测试方案

前端从零搭建，采用 **Vitest + @vue/test-utils + Playwright** 主流组合。

### 5.1 技术选型理由

| 工具 | 用途 | 选型理由 |
|------|------|---------|
| **Vitest** | 单元测试 | Vite 原生集成，零配置，比 Jest 快 3-5 倍 |
| **@vue/test-utils** | 组件测试 | Vue 官方推荐，支持挂载/交互/插槽测试 |
| **@testing-library/vue** | 组件测试（补充） | 以用户视角测试，更接近真实交互 |
| **Playwright** | E2E 测试 | 微软出品，跨浏览器，API 现代化，比 Cypress 更适合多页面 |
| **happy-dom** | DOM 模拟 | 比 jsdom 快，Vitest 默认推荐 |

### 5.2 单元测试（Vitest）

#### 5.2.1 安装依赖（在 shop-frontend 根目录）

```bash
# 安装 Vitest 及相关测试库
pnpm add -Dw vitest @vue/test-utils @testing-library/vue @testing-library/jest-dom happy-dom @vitest/coverage-v8
```

#### 5.2.2 配置文件

在 `shop-frontend` 根目录新建 `vitest.config.ts`：

```typescript
import { defineConfig } from 'vitest/config'
import vue from '@vitejs/plugin-vue'
import path from 'path'

// Vitest 配置
// 小白理解：告诉 Vitest 怎么跑测试，用什么环境，@ 别名指向哪里
export default defineConfig({
  plugins: [vue()],
  test: {
    environment: 'happy-dom',          // DOM 模拟环境
    globals: true,                     // 全局可用 describe/it/expect
    coverage: {
      provider: 'v8',                  // 用 V8 计算覆盖率
      reporter: ['text', 'html', 'lcov'],
      include: ['packages/*/src/**/*.{ts,vue}'],
      exclude: ['**/*.d.ts', '**/main.ts', '**/env.d.ts'],
    },
  },
  resolve: {
    alias: {
      '@': path.resolve(__dirname, 'packages/shared/src'),
    },
  },
})
```

#### 5.4.2 配置文件

在 `shop-frontend` 根目录新建 `playwright.config.ts`：

  testDir: './e2e',
  fullyParallel: true,
  retries: process.env.CI ? 2 : 0,
  reporter: 'html',
  use: {
    baseURL: 'http://localhost:3000',  // web-user 开发地址

## 七、性能测试方案

### 7.1 工具选型

| 工具 | 用途 | 选型理由 |
|------|------|---------|
| **JMeter** | 压力测试 | 主流、可视化、支持分布式 |
| **Gatling**（可选） | 高并发压测 | 代码化场景，性能更高 |
| **Sentinel Dashboard** | 实时限流监控 | 项目已集成，直接使用 |

### 7.2 性能测试场景

| 场景 | 目标 QPS | 目标 P99 | 并发用户数 | 持续时间 |
|------|---------|---------|-----------|---------|
| 商品详情查询（普通） | 500 | 200ms | 100 | 5min |
| 商品详情查询（热点 ID=10086） | 2000 | 500ms | 400 | 5min |
| 秒杀抢购 | 2000 | 1s | 1000 | 1min |
| 用户登录 | 200 | 300ms | 50 | 5min |
| 创建订单 | 100 | 500ms | 50 | 5min |
| 首页加载 | 300 | 300ms | 100 | 5min |

### 7.3 性能测试流程

1. **基准测试**：单接口压测，确定单机性能基线
2. **负载测试**：逐步加压，找到系统拐点
3. **压力测试**：超过拐点持续压测，验证降级与熔断是否生效
4. **稳定性测试**：目标 QPS 持续 24h，验证内存泄漏与连接泄漏
5. **容量评估**：根据结果给出扩容建议

### 7.4 性能指标关注点

- **响应时间**：P50 / P95 / P99
- **吞吐量**：QPS / TPS
- **错误率**：< 0.1%
- **资源使用率**：CPU < 75%、内存 < 80%、磁盘 IO
- **中间件**：Redis 命中率、MySQL 慢查询、MQ 堆积

## 九、CI/CD 集成

### 9.1 测试流水线（GitHub Actions / Jenkins 示例）

```yaml
# .github/workflows/test.yml
# 小白理解：每次提交代码，自动跑测试，测试不过就不让合并
name: CI Test Pipeline

on:
  pull_request:
    branches: [main, develop]
  push:
    branches: [main, develop]

jobs:
  backend-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Setup Java 21
        uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
      - name: Cache Maven
        uses: actions/cache@v3
        with:
          path: ~/.m2
          key: ${{ runner.os }}-m2-${{ hashFiles('**/pom.xml') }}
      - name: Run Backend Tests
        run: mvn clean test  # 跑所有后端测试，JaCoCo 自动生成覆盖率
      - name: Upload Coverage
        uses: actions/upload-artifact@v4
        with:
          name: backend-coverage
          path: '**/target/site/jacoco/'

  frontend-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Setup Node 18
        uses: actions/setup-node@v4
        with:
          node-version: '18'
      - name: Install pnpm
        run: npm install -g pnpm
      - name: Install Dependencies
        working-directory: shop-frontend
        run: pnpm install --frozen-lockfile
      - name: Run Unit Tests
        working-directory: shop-frontend
        run: pnpm test:unit --coverage
      - name: Run E2E Tests
        working-directory: shop-frontend
        run: pnpm test:e2e

  quality-gate:
    needs: [backend-test, frontend-test]
    runs-on: ubuntu-latest
    steps:
      - name: 质量门禁检查
        run: echo "覆盖率达标，允许合并"
```

### 9.2 质量门禁规则

| 指标 | 门禁阈值 | 不通过后果 |
|------|---------|-----------|
| 后端单元测试 | 全部通过 | 阻止合并 |
| 后端行覆盖率 | ≥ 60% | 阻止合并 |
| 前端单元测试 | 全部通过 | 阻止合并 |
| 前端行覆盖率 | ≥ 50% | 阻止合并 |
| E2E 测试 | 全部通过 | 阻止合并 |
| Lint 检查 | 无 Error | 阻止合并 |

## 十二、总结

本测试方案的核心思路：

1. **后端**：在已有的 JUnit 5 + Mockito 单元测试基础上，补充切片测试（@WebMvcTest）、DAO 测试（H2）、集成测试（Testcontainers）、契约测试、覆盖率（JaCoCo）
2. **前端**：从零搭建 Vitest + @vue/test-utils + Playwright 主流组合
3. **API**：Apifox 管理 + 可选 REST Assured 代码化
4. **性能**：JMeter 压测 + Sentinel 实时监控
5. **安全**：OWASP ZAP + Dependency-Check + 代码审查
6. **CI/CD**：GitHub Actions 自动化流水线 + 质量门禁

落地优先级建议（从高到低）：
1. 补全后端核心业务单元测试（订单、秒杀、支付）
2. 搭建前端 Vitest + 组件测试基础设施
3. 添加 JaCoCo 覆盖率与质量门禁
4. 搭建 Testcontainers 集成测试
5. 搭建 Playwright E2E 测试
6. 性能与安全测试
