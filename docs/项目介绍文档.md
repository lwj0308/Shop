# 项目介绍文档 - Shop 电商平台

> 适用人群：初级Java开发者 / 初学者
> 项目类型：微服务电商平台（学习项目）
> 技术栈：Spring Boot 4 + Spring Cloud 2025 + Spring Cloud Alibaba + MySQL + Redis + RocketMQ + Elasticsearch + MinIO

---

## 一、项目简介

本项目是一个**电商平台学习项目**，采用**微服务架构**，包含用户端、商家端和管理端三个前端应用，以及多个后端微服务。项目覆盖了电商系统的核心业务链路：用户注册登录 → 浏览商品 → 加入购物车 → 下单支付 → 物流跟踪 → 退款售后。

### 1.1 项目目标

- 学习微服务架构的设计与实现
- 理解分布式事务、消息队列、搜索引擎等中间件在实际业务中的使用
- 掌握 Spring Cloud Alibaba 全家桶的使用（Nacos、Seata、OpenFeign等）
- 了解电商系统的核心业务流程与技术解决方案

### 1.2 三大客户端

| 客户端 | 面向人群 | 核心功能 |
|--------|---------|---------|
| **用户端** | 普通消费者 | 注册/登录、商品浏览、搜索、购物车、下单、支付、评价 |
| **商家端** | 商家/卖家 | 开店申请、商品发布、库存管理、订单发货、结算 |
| **管理端** | 平台管理员 | 用户管理、商家审核、商品管理、订单管理、数据统计、权限管理 |

### 2.2 架构特点

1. **前后端分离**：后端提供REST API，前端使用Vue 3独立部署
2. **微服务架构**：按业务领域拆分成多个独立服务
3. **统一网关**：所有请求经过Gateway进行鉴权和路由
4. **中间件解耦**：消息队列处理异步任务，搜索引擎处理复杂查询

## 三、微服务模块详解

### 3.1 shop-gateway（网关服务）

**端口**：8844
**职责**：所有外部请求的统一入口

**核心功能**：
1. **路由转发**：根据请求路径转发到对应微服务
   - `/api/user/**` → shop-user
   - `/api/product/**` → shop-product
   - `/api/cart/**` → shop-cart
   - `/api/order/**` → shop-order
   - `/api/payment/**` → shop-payment
   - `/api/merchant/**` → shop-merchant
   - `/api/marketing/**` → shop-marketing
   - `/api/seckill/**` → shop-seckill
   - `/api/admin/**` → shop-admin
2. **权限校验**：使用Sa-Token校验登录状态
3. **Header传递**：解析Token后，将`userId`、角色信息放入请求头传递给下游服务
4. **白名单机制**：登录、注册、商品浏览等接口无需鉴权
5. **防伪造Header**：清除外部传入的敏感Header，由网关统一写入
6. **接口限流**（核心亮点）：Redis + Lua 滑动窗口算法
   - 双维度限流：IP 级别（防爬虫刷接口）+ 接口级别（保护后端服务）
   - 用户维度限流：登录用户按 `rate_limit:user:{userId}` 单独计数（防单用户高频刷接口）
   - 分级限流规则：认证接口 5 QPS、秒杀 3 QPS、下单支付 10 QPS、默认 50 QPS
   - 滑动窗口算法：基于 Redis ZSET，避免固定窗口的临界突发问题
   - Lua 脚本原子执行：检查+扣减在 Redis 单线程内完成，无并发问题
   - 降级策略：Redis 异常时放行请求（限流是弱依赖，不阻断主流程）
   - 多实例共享：多个 Gateway 实例共享同一份限流计数
7. **黑白名单机制**（RL-11 引入）：IP 维度的精准访问控制
   - 黑名单：Redis Set 存储被封禁 IP，请求返回 403，自动 1 小时过期
   - 白名单：白名单内 IP 跳过限流检查（内部运维 IP、合作方 IP）
   - 自动拉黑：单 IP 触发限流超 10 次自动加入黑名单（防恶意刷接口）
   - 弱依赖：Redis 异常时放行请求，不阻断主流程
8. **XSS 防护**：请求体敏感字符过滤

**关键代码位置**：
- 鉴权过滤器：[AuthGlobalFilter.java](file:///d:/workspace/business/Shop/shop-gateway/src/main/java/com/shop/gateway/filter/AuthGlobalFilter.java)
- 限流过滤器：[RateLimitFilter.java](file:///d:/workspace/business/Shop/shop-gateway/src/main/java/com/shop/gateway/filter/RateLimitFilter.java)
- 黑名单过滤器：[BlacklistFilter.java](file:///d:/workspace/business/Shop/shop-gateway/src/main/java/com/shop/gateway/filter/BlacklistFilter.java)
- 限流配置类：[RateLimitProperties.java](file:///d:/workspace/business/Shop/shop-gateway/src/main/java/com/shop/gateway/config/RateLimitProperties.java)

### 3.3 shop-product（商品服务）

**端口**：8847
**职责**：商品全生命周期管理 + 搜索

**核心功能**：
1. **分类管理**：树形多级分类
2. **品牌管理**：品牌CRUD
3. **商品管理**：SPU/SKU双层结构
   - SPU（标准产品单位）：如"iPhone 15"
   - SKU（库存单位）：如"iPhone 15 红色 128G"
4. **商品评价**：用户评价、商家回复
5. **商品搜索**（核心亮点）：
   - 使用Elasticsearch实现全文检索
   - 支持ik中文分词
   - 支持分类/品牌/价格区间筛选
   - 支持排序
   - 关键词高亮
   - 聚合（品牌聚合、分类聚合）
   - 搜索建议（suggest）
   - 热门搜索词（Redis ZSet + 时间衰减算法）
6. **库存扣减**（核心亮点）：
   - 使用Redis + Lua脚本实现高性能、原子性的库存扣减
   - 幂等性保证：同一订单号不会重复扣减
7. **接口限流**（核心亮点，多层防护）：
   - **方法级限流**：Sentinel `@SentinelResource` 注解保护核心接口（如商品详情、库存扣减）
   - **热点参数限流**（RL-12）：商品详情接口按 `productId` 维度独立限流
     - 普通商品：500 QPS / 爆款商品（ID=10086）：2000 QPS
     - 触发限流时返回 Caffeine 本地缓存的商品数据（不直接拒绝请求）
   - **系统自适应限流**（RL-15）：CPU > 75%、Load > 4.0、RT > 10ms 时全局收紧限流

**核心数据表**：
- `category`：分类（树形）
- `brand`：品牌
- `product`：商品SPU
- `product_spec`：规格模板（颜色、尺码等）
- `product_spec_value`：规格值
- `product_sku`：商品SKU（含库存和乐观锁version）
- `product_image`：商品图片
- `product_comment`：商品评价

### 3.5 shop-order（订单服务）

**端口**：8849
**职责**：订单全生命周期管理（核心服务）

**核心功能**：
1. **创建订单**（核心链路）：
   - 幂等校验（Redis判断是否重复下单）
   - 分布式锁（防止同一用户并发下单）
   - Feign调用商品服务扣减库存（Seata分布式事务）
   - 发送RocketMQ延时消息（30分钟超时自动取消）
   - 删除购物车中已下单的商品
2. **取消订单**：用户主动取消 → 回滚库存
3. **确认收货**：用户确认收到商品
4. **超时自动取消**：RocketMQ延时消息消费
5. **支付回调处理**：支付成功后更新订单状态
6. **退款管理**：用户申请退款 → 商家审核 → 退款
7. **物流跟踪**：物流信息管理
8. **接口限流**（核心亮点）：
   - **方法级限流**：Sentinel 保护订单创建、秒杀抢购接口（QPS 超限走降级）
   - **Feign 降级**：9 个 Feign 客户端配置 FallbackFactory，下游服务故障时返回降级数据
   - **系统自适应限流**（RL-15）：大促场景 CPU/负载超阈值时全局收紧

**核心数据表**：
- `order_info`：订单主表
- `order_item`：订单明细（含价格/规格快照）
- `order_address`：收货地址快照（防止用户修改地址影响已有订单）
- `order_logistics`：物流信息
- `order_log`：订单状态变更日志（审计用）
- `refund_order`：退款单

**关键代码位置**：

## 五、中间件使用详解

### 5.2 Redis（缓存 + 分布式锁）

**Redis用途**：

| 功能 | Key格式 | 说明 |
|------|---------|------|
| **Sa-Token会话** | `satoken:login:token:{token}` | 存储用户登录状态 |
| **库存缓存** | `stock:sku:{skuId}` | SKU可用库存，Lua脚本扣减 |
| **库存扣减记录** | `stock:deduct:{skuId}` | Set结构，存已扣减的订单号 |
| **库存回滚记录** | `stock:rollback:{skuId}` | Set结构，存已回滚的订单号 |
| **热门搜索词** | `product:hot_keywords` | ZSet结构，存搜索词+热度分数 |
| **下单分布式锁** | `order:create:{userId}` | 防止同一用户并发下单 |
| **幂等Token** | `order:idempotent:{token}` | 防止用户重复提交订单 |
| **接口限流-IP维度** | `rate_limit:ip:{ip}` | ZSet结构，存请求时间戳，滑动窗口限流 |
| **接口限流-路径维度** | `rate_limit:path:{path}` | ZSet结构，存请求时间戳，滑动窗口限流 |
| **接口限流-用户维度** | `rate_limit:user:{userId}` | ZSet结构，登录用户单独计数（防单用户刷接口） |
| **IP黑名单** | `blacklist:ip` | Set结构，被封禁IP集合，自动1小时过期 |
| **秒杀库存** | `seckill:stock:{seckillId}` | 秒杀活动可用库存，Lua脚本原子扣减 |
| **秒杀购买记录** | `seckill:user:{seckillId}` | 记录用户是否已抢购，防重复抢购 |

**核心亮点 - Redis + Lua脚本扣库存**（在`StockServiceImpl.java`中）：
- Lua脚本在Redis中**原子执行**，天然防止并发问题
- 比数据库乐观锁性能更高（减少数据库压力）
- 支持幂等：同一订单号不会重复扣减

**核心亮点 - Redis + Lua滑动窗口限流**（在`RateLimitFilter.java`中）：
- 用 ZSET 存储请求时间戳，`ZREMRANGEBYSCORE` 移除窗口外旧记录实现"滑动"
- Lua 脚本保证"检查+扣减"原子性，无并发问题
- 多 Gateway 实例共享同一份限流计数（内存版只能单机限流）
- Redis 异常时降级放行（限流是弱依赖，不阻断主流程）

### 5.3 RocketMQ（消息队列）

**使用场景**：

| Topic | 生产者 | 消费者 | 用途 |
|-------|--------|--------|------|
| `topic_order_timeout` | shop-order | shop-order | 订单超时自动取消（30分钟延时消息） |
| `topic_payment_callback` | shop-payment | shop-order | 支付成功通知订单服务更新状态 |
| `product_sync_topic` | shop-product | shop-product | 商品变更同步到Elasticsearch |
| `topic_seckill_order` | shop-seckill(或shop-order) | shop-order | 秒杀抢购成功后异步创建订单 |

**消息队列的好处（小白理解）**：
1. **异步解耦**：支付服务不用等订单服务处理完，发完消息就可以返回给用户
2. **削峰填谷**：大促时大量支付回调不会把订单服务压垮
3. **可靠投递**：即使订单服务暂时挂了，消息不会丢，等服务恢复后继续消费

### 5.4 Elasticsearch（搜索引擎）

**索引**：`product`（商品索引）

**核心功能**：

2. **筛选**：分类、品牌、价格区间

- ES支持中文分词，搜索更智能（搜"手机"也能找到"智能手机"）

## 六、多层限流防护体系（核心亮点）

本项目实现了**从入口到资源层的 7 层限流防护**，是项目最大的技术亮点之一。每一层都有明确的职责，层层递进，确保系统在高并发场景下稳定运行。

### 6.1 防护架构总览

```
请求流入
   ↓
┌──────────────────────────────────────────────────────────────────┐
│ 第1层  网关限流（Gateway RateLimitFilter）                        │
│   Redis + Lua 滑动窗口，IP/路径/用户三维度分级限流                  │
└──────────────────────────────────────────────────────────────────┘
   ↓
┌──────────────────────────────────────────────────────────────────┐
│ 第2层  黑白名单（BlacklistFilter，Order=-85）                     │
│   黑名单 IP 直接返回 403，白名单 IP 跳过限流                       │
└──────────────────────────────────────────────────────────────────┘
   ↓
┌──────────────────────────────────────────────────────────────────┐
│ 第3层  Sentinel 方法级限流（@SentinelResource）                   │
│   保护核心接口：商品详情、库存扣减、订单创建、秒杀抢购              │
└──────────────────────────────────────────────────────────────────┘
   ↓
┌──────────────────────────────────────────────────────────────────┐
│ 第4层  Sentinel 热点参数限流（ParamFlowRule）                      │
│   商品详情按 productId 单独限流，爆款商品配更高阈值                 │
└──────────────────────────────────────────────────────────────────┘
   ↓
┌──────────────────────────────────────────────────────────────────┐
│ 第5层  Sentinel 熔断降级（DegradeRule + Feign Fallback）          │
│   异常率/慢调用超阈值自动熔断，Feign 调用失败走降级逻辑            │
└──────────────────────────────────────────────────────────────────┘
   ↓
┌──────────────────────────────────────────────────────────────────┐
│ 第6层  Sentinel 系统自适应限流（SystemRule）                       │
│   CPU > 75%、Load > 4.0、RT > 10ms 时全局收紧限流（兜底）         │
└──────────────────────────────────────────────────────────────────┘
   ↓
┌──────────────────────────────────────────────────────────────────┐
│ 第7层  资源层保护 + 前端防抖                                       │
│   Tomcat 线程池 / Lettuce 连接池 / HikariCP 数据库连接池           │
│   前端按钮防抖（useDebounce，1秒冷却，防重复提交）                 │
└──────────────────────────────────────────────────────────────────┘
   ↓
请求到达业务逻辑
```

### 6.2 各层职责详解

#### 第 1 层：网关限流（Redis + Lua 滑动窗口）

**位置**：`shop-gateway` 的 `RateLimitFilter`（Order=-80）

**算法**：Redis ZSET 滑动窗口
- 用 ZSET 存储请求时间戳，`ZREMRANGEBYSCORE` 移除窗口外旧记录
- `ZCARD` 统计当前窗口内请求数，超限则拒绝
- Lua 脚本保证"检查+扣减"原子性

**三维度限流**：
| 维度 | Key 格式 | 用途 |
|------|---------|------|
| IP 维度 | `rate_limit:ip:{ip}` | 防爬虫刷接口 |
| 路径维度 | `rate_limit:path:{path}` | 保护单个接口 |
| 用户维度 | `rate_limit:user:{userId}` | 防单用户高频刷接口（仅登录用户） |

**分级限流规则**（Nacos 配置热更新）：
| 接口类型 | IP QPS | 路径 QPS | 说明 |
|---------|--------|---------|------|
| 认证接口 `/api/user/auth/**` | 5 | 50 | 防密码爆破、短信轰炸 |
| 秒杀接口 `/api/seckill/grab/**` | 3 | 1000 | 防刷单 |
| 下单支付 `/api/order/**` | 10 | 100 | 防恶意占库存 |
| 评论提交 `/api/product/comment/create` | 3 | 50 | 防刷评 |
| 默认 | 50 | 200 | 通用保护 |

**降级策略**：Redis 异常时放行请求（限流是弱依赖，不阻断主流程）

#### 第 2 层：黑白名单（BlacklistFilter）

**位置**：`shop-gateway` 的 `BlacklistFilter`（Order=-85，先于限流过滤器执行）

**黑名单机制**：
- Redis Set 存储被封禁 IP，请求返回 403
- 自动 1 小时过期，到期自动解封
- **自动拉黑**：单 IP 触发限流超 10 次，自动加入黑名单（防恶意刷接口）

**白名单机制**：
- 白名单内 IP 跳过限流检查（内部运维 IP、合作方 IP）
- 配置在 Nacos `shop-gateway.yml`，支持热更新

**弱依赖**：Redis 异常时放行请求，不阻断主流程

#### 第 3 层：Sentinel 方法级限流

**位置**：shop-product、shop-order、shop-seckill 的 `@SentinelResource` 注解

**保护范围**（5 条硬编码规则 + Nacos 动态规则）：
| 服务 | 资源名 | QPS 阈值 | 说明 |
|------|--------|---------|------|
| shop-product | `stock:deduct` | 1000 | 库存扣减 |
| shop-product | `product:list` | 动态 | 商品列表 |
| shop-order | `order:create` | 100 | 订单创建 |
| shop-order | `seckill:grab` | 2 | 秒杀抢购（测试值） |
| shop-seckill | `seckill:activity:create` | 50 | 秒杀活动创建 |
| shop-seckill | `seckill:activity:offline` | 50 | 秒杀活动下架 |

**规则持久化**：所有规则存储在 Nacos `SENTINEL_GROUP` 分组，支持动态修改
- `shop-*-flow-rules.json`：限流规则
- `shop-*-degrade-rules.json`：熔断降级规则
- `shop-*-param-rules.json`：热点参数规则
- `shop-*-system-rules.json`：系统自适应规则

#### 第 4 层：热点参数限流（RL-12）

**位置**：shop-product 的 `ProductServiceImpl.detail()` 方法

**场景**：商品详情接口按 `productId` 维度独立限流
- 普通商品：500 QPS（默认阈值）
- 爆款商品（ID=10086）：2000 QPS（专门配置更高阈值）

**降级策略**（核心亮点）：触发限流时不直接拒绝请求，而是返回 Caffeine 本地缓存的商品数据
- `@SentinelResource(blockHandler = "detailBlockHandler")`
- `detailBlockHandler` 捕获 `ParamFlowException`，从 Caffeine 读取缓存数据返回
- 用户无感知，体验更好

**规则配置**：Nacos `shop-product-param-rules.json`，支持动态刷新

#### 第 5 层：Sentinel 熔断降级

**两种降级机制**：

1. **Sentinel DegradeRule**（接口级熔断）
   - 慢调用比例超阈值 → 熔断
   - 异常率超阈值 → 熔断
   - 规则存储在 Nacos `shop-*-degrade-rules.json`

2. **Feign FallbackFactory**（服务间调用降级，RL-03 引入）
   - 9 个服务全部启用 `feign.sentinel.enabled=true`
   - 31 个 Feign 客户端配置 FallbackFactory
   - 下游服务故障时返回降级数据，而非抛 500 错误
   - 例：shop-order 调用 shop-product 失败 → 返回缓存数据或友好提示

**关键代码位置**：
- 各服务的 `feign/fallback/` 目录下的 `*FallbackFactory.java`

#### 第 6 层：系统自适应限流（RL-15）

**位置**：shop-product、shop-order、shop-seckill 的 `SentinelSystemRuleConfig.java`

**设计理念**（小白理解）：
- 普通限流像每个路口设红绿灯（每个接口独立限流）
- 系统限流像交警大队的总指挥，看到整条路都堵了（CPU 飙高），直接拉警报让所有路口都延长红灯时间

**5 条系统规则**（任一触发即全局收紧限流）：
| 指标 | 阈值 | 说明 |
|------|------|------|
| CPU 使用率 | > 75% | CPU 忙不过来了 |
| 系统负载 | > 4.0 | 4 核机器满载是 4.0 |
| 平均响应时间 | > 10ms | 请求处理变慢了 |
| 入口总 QPS | > 2000 | 请求量太大了 |
| 入口总线程数 | > 100 | 并发线程太多了 |

**双层保护**：
- **硬编码兜底**（@PostConstruct）：服务启动时加载，即使 Nacos 不可用也能生效
- **Nacos 动态配置**（`shop-*-system-rules.json`）：运行时修改阈值无需重启

#### 第 7 层：资源层保护 + 前端防抖

**资源层调优**（RL-07）：
| 资源 | 配置 | 说明 |
|------|------|------|
| Tomcat 线程池 | max-threads=200, max-connections=8192, accept-count=100 | 防止线程池耗尽 |
| Lettuce 连接池 | max-active=16, max-idle=8, min-idle=2, max-wait=5000ms | 防止 Redis 连接耗尽 |
| HikariCP 数据库连接池 | maximum-pool-size=20, minimum-idle=5 | 防止数据库连接耗尽 |

**前端按钮防抖**（RL-08）：
- `useDebounce` Composable，1 秒冷却，防止用户快速连续点击
- 应用场景：提交订单、秒杀抢购、加入购物车
- 关键代码：[useDebounce.ts](file:///d:/workspace/business/Shop/shop-frontend/packages/shared/src/composables/useDebounce.ts)

### 6.4 限流后处理策略（RL-13）

当限流触发时，系统支持多种后处理策略，而非简单拒绝：

| 策略 | 适用场景 | 实现方式 |
|------|---------|---------|
| **直接拒绝** | 默认策略 | 返回 429 状态码 |
| **排队等待** | 秒杀抢购 | 返回 202 + 排队号，前端轮询队列位置 |
| **缓存降级** | 商品详情（热点参数限流） | 返回 Caffeine 本地缓存数据 |
| **Feign 降级** | 服务间调用 | FallbackFactory 返回降级数据 |

**秒杀排队机制**（核心亮点）：
- 秒杀抢购被限流时返回 202 状态码 + 排队号
- 前端轮询排队位置，轮到时自动重试抢购
- 超过 10 次重试放弃，提示用户稍后重试
- 关键代码：[seckill/DetailView.vue](file:///d:/workspace/business/Shop/shop-frontend/packages/web-user/src/views/seckill/DetailView.vue)

### 6.5 限流与幂等联动（RL-14）

下单接口的限流与幂等机制协同工作：
- 前端通过 `X-Idempotent-Key` Header 传递幂等键
- 后端用 Redis `SETNX` 占用幂等键，防止限流重试导致重复下单
- 限流触发后前端重试时，幂等键保证不会创建重复订单

## 七、核心业务流程

### 7.1 用户下单全流程

```
用户浏览商品 → 加入购物车 → 去结算 → 提交订单 → 支付 → 等待发货 → 收货确认
     ↓              ↓          ↓         ↓         ↓           ↓          ↓
  ES搜索       Redis缓存   校验库存   ①创建订单  ②支付回调   ③发货      确认收货
                          扣减库存   (Seata     (RocketMQ)    (商家)      (更新状态)
                          分布式事务)
                          ↓
                      ④发送延时消息(30分钟)
                          ↓
                      超时未支付 → 自动取消 → 回滚库存
```

**下单步骤详解**（`OrderServiceImpl.createOrder`）：
1. **幂等校验**：检查前端传递的幂等Token是否已使用
2. **获取分布式锁**：同一用户不能同时创建多个订单
3. **Feign获取商品信息**：校验SKU是否存在、库存是否充足
4. **Feign获取地址信息**：校验收货地址
5. **生成订单号**：雪花算法生成全局唯一订单号
6. **计算金额 + 创建订单**：插入order_info、order_item、order_address
7. **Feign调用扣减库存**：通过Seata分布式事务保证一致性
8. **发送RocketMQ延时消息**：30分钟后检查是否支付
9. **删除购物车中已下单商品**（失败不影响主流程，记录日志即可）
10. **释放分布式锁**

### 7.2 支付流程

```
用户支付 → 第三方支付平台 → 支付回调 → shop-payment处理 → 发送MQ消息 → shop-order消费
                ↓                                                     ↓
         返回支付结果                                            更新订单状态为"已支付"
```

### 7.3 商品搜索流程

```
用户输入关键词 → Gateway → shop-product → ES搜索（分词+筛选+排序+高亮+聚合）→ 合并实时价格/库存 → 返回结果
```

## 八、项目亮点

### 1. 分布式事务（Seata）
- 下单扣库存涉及跨服务数据一致性
- 使用Seata AT模式，自动生成回滚日志

### 2. 高性能库存扣减（Redis + Lua）
- Redis内存操作，速度极快
- Lua脚本原子执行，天然防并发
- 幂等性设计，防止重复扣减

### 3. 超时订单自动取消（RocketMQ延时消息）
- 下单时发送延时消息（等级16 = 30分钟）
- 消息消费时检查订单是否已支付
- 未支付则自动取消并回滚库存

### 4. 全文检索（Elasticsearch）
- ik中文分词
- 多维度筛选 + 排序 + 高亮 + 聚合
- 搜索建议 + 热门搜索词

### 5. 统一网关鉴权
- 所有请求经过Gateway
- Header防伪造
- Token自动续期
- 白名单机制

### 6. 多层限流防护体系（核心亮点，详见第六章）
- **7 层防护**：从入口到资源层层递进，确保高并发场景稳定
  - 第 1 层：网关限流（Redis + Lua 滑动窗口，IP/路径/用户三维度）
  - 第 2 层：黑白名单（IP 封禁 + 自动拉黑机制）
  - 第 3 层：Sentinel 方法级限流（@SentinelResource 保护核心接口）
  - 第 4 层：热点参数限流（爆款商品配更高阈值，触发时返回缓存数据）
  - 第 5 层：Sentinel 熔断降级 + Feign Fallback（服务故障自动降级）
  - 第 6 层：系统自适应限流（CPU/Load/RT 超阈值全局收紧，兜底保护）
  - 第 7 层：资源层调优 + 前端按钮防抖（连接池 + useDebounce）
- **多种后处理策略**：直接拒绝、排队等待（秒杀）、缓存降级、Feign 降级
- **规则动态管理**：Sentinel Dashboard 可视化 + Nacos 配置热更新
- **限流与幂等联动**：防止限流重试导致重复下单

### 7. 完整的权限体系（管理端RBAC）
- 用户-角色-权限三层结构
- 数据权限控制（部门数据隔离）
- 操作日志记录

### 8. 订单状态机
- 严格的状态流转校验
- 防止非法操作（如未付款订单不能发货）
- 状态变更全记录（order_log）

### 9. 数据快照机制
- 地址快照：下单时复制地址，防止用户修改影响历史订单
- 价格快照：SKU价格随订单保存，不受后续调价影响

### 10. 乐观锁防并发
- 账户表：用户余额/积分修改
- SKU表：库存修改（降级方案）
- 订单状态更新

### 11. Nacos配置中心
- 配置集中管理
- 支持多环境配置
- 配置热更新（无需重启服务）

## 九、项目可改进/不足之处

### 9.1 功能不足

1. **支付方式单一**：目前只有支付流程框架，未对接真实的支付宝/微信支付
2. **物流对接**：未对接真实物流API，物流信息需手动录入
3. **推荐系统**：目前只有浏览足迹数据，未实现个性化推荐
4. **用户评价体系**：评价功能简单，缺少追评、晒单等
5. **商家结算系统**：结算功能不完善，缺少对账、提现等
6. **后台数据统计**：Dashboard仅有基础数据，缺少可视化图表
7. **消息通知**：下单、发货等状态变更未实现站内信/短信通知
8. **文件上传前端**：MinIO后端已就绪，但前端上传组件可能不完善

### 9.2 架构/技术可优化

1. **服务熔断降级**：已集成 Sentinel 实现方法级限流、熔断降级、系统自适应限流（详见第六章），未来可进一步引入集群流控（RL-09）支持多实例精确限流
2. **链路追踪**：未集成SkyWalking/Zipkin，定位问题依赖日志
3. **分布式ID**：订单号使用雪花算法，但workerId未做服务区分
4. **数据库分库分表**：数据量大时需要考虑ShardingSphere
5. **二级缓存**：Caffeine + Redis 多级缓存可进一步提升性能（商品详情已用 Caffeine 做热点参数限流降级）
6. **缓存预热**：系统启动时未进行缓存预热
7. **缓存击穿/穿透**：热门商品缓存失效时可能打垮数据库
8. **接口幂等性**：下单接口已实现幂等（X-Idempotent-Key + Redis SETNX），其他接口可进一步完善
9. **限流**：已实现 7 层限流防护体系（网关限流 + 黑白名单 + Sentinel 方法级/热点参数/熔断降级/系统自适应 + 资源层调优 + 前端防抖），详见第六章
10. **日志收集**：ELK/EFK日志系统未集成
11. **监控告警**：Prometheus + Grafana监控未集成
12. **容器化部署**：Docker Compose可运行但缺少K8s部署方案

### 9.3 安全可加强

1. **敏感数据加密**：手机号等只有框架，实际加密逻辑需完善
2. **XSS/CSRF防护**：前端和后端都需进一步加固
3. **SQL注入防护**：MyBatis-Plus已防SQL注入，但手写SQL需审查
4. **接口防刷**：已实现 7 层限流防护（IP/路径/用户三维度限流 + 黑白名单 + 自动拉黑机制），详见第六章
5. **密码策略**：缺少密码强度校验、定期修改等

### 9.4 代码/工程

1. **单元测试**：项目缺少单元测试覆盖
2. **API文档**：SpringDoc配置存在但可能不完善
3. **代码注释**：部分模块注释较少
4. **异常处理**：全局异常处理需要统一规范
