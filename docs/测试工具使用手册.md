## 二、JaCoCo - Java 代码覆盖率工具

### 2.1 这是什么？（小白版）

**JaCoCo = Java Code Coverage**

简单说：你写了一堆 Java 代码，也写了一些测试用例。JaCoCo 帮你统计——**你的测试用例到底跑过了多少行代码？没跑过的代码就是"覆盖不到"的，可能藏着 bug**。

#### 通俗类比

想象你写了一本 100 页的小说，让朋友帮忙检查错别字。朋友检查了 60 页，那覆盖率就是 60%。剩下 40 页没检查，可能有错别字。

- **行覆盖率（LINE）**：有多少行代码被测试跑过
- **分支覆盖率（BRANCH）**：if/else 的每个分支是否都测过

### 2.2 项目中的配置

配置文件：[pom.xml](file:///d:/workspace/business/Shop/pom.xml#L358-L426)

```xml
<!-- JaCoCo 覆盖率门槛：60% -->
<jacoco.line.coverage>0.60</jacoco.line.coverage>

<!-- JaCoCo 插件配置 -->
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <configuration>
        <!-- 排除不需要测试的类 -->
        <excludes>
            <exclude>com/shop/**/*Application.*</exclude>  <!-- 启动类 -->
            <exclude>com/shop/**/config/**</exclude>       <!-- 配置类 -->
            <exclude>com/shop/**/feign/**</exclude>        <!-- Feign 客户端 -->
            <exclude>com/shop/**/mapper/**</exclude>       <!-- Mapper 接口 -->
            <exclude>com/shop/**/entity/**</exclude>       <!-- 实体类 -->
            <exclude>com/shop/**/dto/**</exclude>          <!-- DTO -->
            <exclude>com/shop/**/vo/**</exclude>           <!-- VO -->
            <!-- ... 其他排除项 -->
        </excludes>
    </configuration>
    <executions>
        <!-- 三个执行阶段 -->
        <execution><id>prepare-agent</id><goals><goal>prepare-agent</goal></goals></execution>
        <execution><id>report</id><phase>test</phase><goals><goal>report</goal></goals></execution>
        <execution><id>check</id><goals><goal>check</goal></goals>
            <configuration>
                <!-- ✅ 质量门禁已启用：覆盖率 < 60% 则构建失败 -->
                <haltOnFailure>true</haltOnFailure>
                <rules>
                    <rule>
                        <element>BUNDLE</element>
                        <limits>
                            <limit>
                                <counter>LINE</counter>
                                <value>COVEREDRATIO</value>
                                <minimum>${jacoco.line.coverage}</minimum>
                            </limit>
                        </limits>
                    </rule>
                </rules>
            </configuration>
        </execution>
    </executions>
</plugin>
```

#### 三个执行阶段（小白理解）

| 阶段 | 作用 | 类比 |
|------|------|------|
| `prepare-agent` | 测试启动前注入探针 | 考场装监控摄像头 |
| `report` | 测试结束后生成报告 | 考完试出成绩单 |
| `check` | 检查覆盖率是否达标 | 不及格就拒绝毕业 |

#### 排除的类为什么不需要测试？

| 排除项 | 原因 |
|--------|------|
| `*Application.*` | 启动类只有 main 方法，框架自动调用 |
| `config/**` | 配置类由集成测试覆盖 |
| `feign/**` | Feign 是接口声明，实际调用由对方服务实现 |
| `mapper/**` | Mapper 接口由 DAO 测试覆盖（H2 数据库） |
| `entity/dto/vo` | 纯数据载体，没有业务逻辑 |

### 2.3 怎么用？

#### 运行测试并生成覆盖率报告

```powershell
# 在项目根目录执行
cd d:\workspace\business\Shop

# 运行所有模块的测试（会自动生成覆盖率报告）
mvn test

# 只测试某个模块
mvn test -pl shop-order

# 跳过测试只生成报告（如果之前已经跑过测试）
mvn jacoco:report
```

#### 查看覆盖率报告

```powershell
# 方式1：打开整个项目的聚合报告（推荐，看到所有模块汇总）
start shop-coverage/target/site/jacoco-aggregate/index.html

# 方式2：打开单个模块的报告
start shop-order/target/site/jacoco/index.html
```

#### 报告解读

HTML 报告中关键列：

| 列名 | 含义 | 看哪个值 |
|------|------|---------|
| **Missed Instructions** | 未执行的指令数 | 越少越好 |
| **Cov.** | 覆盖率百分比 | ≥ 60% 达标 |
| **Missed Lines** | 未执行的行数 | 越少越好 |
| 红色 | 完全未覆盖 | 需要补测试 |
| 黄色 | 部分覆盖（如 if 没测 else） | 需要补分支测试 |
| 绿色 | 完全覆盖 | ✅ |

### 2.4 质量门禁机制

#### 启用后的工作流

```
开发者写代码 → 提交前 mvn test →
  ├─ 测试全通过 → 检查覆盖率 →
  │   ├─ 覆盖率 ≥ 60% → BUILD SUCCESS ✅ 可以提交
  │   └─ 覆盖率 < 60% → BUILD FAILURE ❌ 必须补测试
  └─ 测试失败 → BUILD FAILURE ❌ 必须修复
```

#### 如果构建失败怎么办？

```powershell
# 看哪个模块覆盖率不达标
mvn test -pl shop-order 2>&1 | Select-String "jacoco"

# 典型错误信息：
# Rule violated for bundle shop-order: lines covered ratio is 0.55, but expected minimum is 0.60

# 解决：打开 HTML 报告，找到红色（未覆盖）的类，补对应的测试
start shop-order/target/site/jacoco/index.html
```

### 2.5 临时跳过质量门禁（紧急情况）

```powershell
# 临时跳过覆盖率检查（仅紧急发版时用，不要养成习惯）
mvn test -Djacoco.skip=true
```

⚠️ **警告**：跳过门禁等于自欺欺人，覆盖率会慢慢退化。生产环境永远不要这么做。

### 2.6 调整覆盖率阈值

如果团队决定提高标准（比如从 60% 提到 70%）：

```xml
<!-- 修改 pom.xml 第 75 行 -->
<jacoco.line.coverage>0.70</jacoco.line.coverage>
```

建议渐进式提升：60% → 65% → 70% → 80%，避免一次性提升太多导致全团队构建失败。

## 三、JMeter - 性能压测工具

### 3.1 这是什么？（小白版）

**JMeter = Java Meter（Java 写的测量工具）**

简单说：模拟 1000 个用户同时访问你的网站，看系统扛不扛得住。

#### 通俗类比

开业第一天，你的店只有 1 个收银员。你想知道：
- 100 个顾客同时来，收银员忙得过来吗？（QPS 测试）
- 顾客平均等多久？（响应时间）
- 会不会有顾客等到一半走人？（错误率）

JMeter 就是那个"模拟 1000 个顾客同时来"的工具。

### 3.2 项目中的测试场景

配置文件位置：[perf/jmx/](file:///d:/workspace/business/Shop/perf/jmx/)

| 任务 | 场景 | 目标 QPS | 目标 P99 | 并发数 | 持续时间 |
|------|------|---------|---------|--------|---------|
| N-P-01 | 商品详情查询（普通） | 500 | 200ms | 100 | 5min |
| N-P-02 | 商品详情查询（热点） | 2000 | 500ms | 400 | 5min |
| N-P-03 | 秒杀抢购 | 2000 | 1s | 1000 | 1min |
| N-P-04 | 用户登录 | 200 | 300ms | 50 | 5min |
| N-P-05 | 创建订单 | 100 | 500ms | 50 | 5min |
| N-P-06 | 首页加载 | 300 | 300ms | 100 | 5min |
| N-P-07 | 24h 稳定性测试 | 100 | - | 50 | 24h |
| N-P-08 | 限流降级验证 | - | - | 500 | 1min |

### 3.3 环境准备

#### 第一步：安装 JMeter

1. 下载 JMeter 5.6+：https://jmeter.apache.org/download_jmeter.cgi
2. 解压到 `D:\Apache-JMeter-5.6.3`
3. 设置环境变量：

```powershell
# 永久设置（推荐）
[Environment]::SetEnvironmentVariable("JMETER_HOME", "D:\Apache-JMeter-5.6.3", "User")
$env:PATH += ";D:\Apache-JMeter-5.6.3\bin"

# 验证
jmeter --version
```

#### 第二步：启动后端服务

确保 11 个微服务 + Redis + MySQL + RocketMQ + Nacos 全部启动。

#### 第三步：准备测试数据

```powershell
cd d:\workspace\business\Shop

# 一键准备（会执行 SQL + 预热 Redis）
.\perf\scripts\run-perf.ps1 -Scenario N-P-01 -SkipCleanup
```

### 3.4 怎么用？

#### 方式1：一键运行（推荐）

```powershell
cd d:\workspace\business\Shop

# 运行所有 P0 场景（不含 24h 稳定性测试）
.\perf\scripts\run-perf.ps1 -Scenario all

# 只运行单个场景
.\perf\scripts\run-perf.ps1 -Scenario N-P-01

# 运行多个场景
.\perf\scripts\run-perf.ps1 -Scenario N-P-01,N-P-02,N-P-06

# 跳过数据准备（已准备过数据时）
.\perf\scripts\run-perf.ps1 -Scenario N-P-01 -SkipDataPrep
```

#### 方式2：手动运行单个场景

```powershell
cd d:\workspace\business\Shop

# 命令行模式运行（推荐，性能更好）
jmeter -n -t perf/jmx/N-P-01-product-detail-normal.jmx `
       -l perf/results/N-P-01-result.jtl `
       -e -o perf/results/N-P-01-report

# 运行完成后查看 HTML 报告
start perf/results/N-P-01-report/index.html
```

#### 参数说明

| 参数 | 说明 |
|------|------|
| `-n` | 非 GUI 模式（命令行模式，压测时必须用这个，GUI 模式会消耗资源影响结果） |
| `-t` | 指定测试计划文件（.jmx） |
| `-l` | 指定结果文件（.jtl） |
| `-e` | 测试结束后生成 HTML 报告 |
| `-o` | 指定 HTML 报告输出目录（必须是空目录） |

#### 方式3：GUI 模式（仅用于编辑脚本，不用于压测）

```powershell
# 打开 GUI 界面编辑测试计划
jmeter -t perf/jmx/N-P-01-product-detail-normal.jmx
```

⚠️ **警告**：GUI 模式会消耗大量内存，**绝对不要用 GUI 模式跑压测**，结果不准。

### 3.5 测试结果解读

#### 关键指标

打开 `perf/results/N-P-01-report/index.html`，重点看：

| 指标 | 含义 | 达标标准 |
|------|------|---------|
| **Throughput** | 吞吐量（每秒处理多少请求） | ≥ 目标 QPS |
| **90th pct** | 90% 的请求响应时间低于此值 | < 目标 P99 |
| **95th pct** | 95% 的请求响应时间低于此值 | < 目标 P99 |
| **99th pct** | 99% 的请求响应时间低于此值（P99） | < 目标 P99 |
| **Error Rate** | 错误率 | < 0.1% |

#### 通俗解释

- **QPS = 500** 意味着：系统每秒能处理 500 个请求
- **P99 = 200ms** 意味着：99% 的用户在 200ms 内收到响应，只有 1% 的用户超过 200ms
- **Error Rate = 0.1%** 意味着：1000 个请求里有 1 个出错

### 3.6 各场景注意事项

#### N-P-03 秒杀测试


## 四、Vitest - 前端单元测试工具

### 4.1 这是什么？（小白版）

**Vitest = Vite Test**

简单说：和后端的 JUnit 一样，用来测前端代码（Vue 组件、TypeScript 工具函数）。

#### 通俗类比

你写了一个按钮组件 `<el-button>`，想验证：
- 点击后会不会触发事件？
- 传不同的 props，显示的文字对不对？
- 禁用状态下能不能点？

Vitest 就是帮你自动点按钮、检查显示的工具。

### 4.2 项目中的配置

每个前端包都有独立的 `vitest.config.ts`：

| 包 | 配置文件 | 环境 | 覆盖率门槛 |
|----|---------|------|----------|
| shared | [vitest.config.ts](file:///d:/workspace/business/Shop/shop-frontend/packages/shared/vitest.config.ts) | node | 50% |
| web-user | [vitest.config.ts](file:///d:/workspace/business/Shop/shop-frontend/packages/web-user/vitest.config.ts) | happy-dom | 50% |
| web-merchant | vitest.config.ts | happy-dom | 50% |
| web-admin | vitest.config.ts | happy-dom | 50% |

#### 配置示例（web-user）

```typescript
export default defineConfig({
  plugins: [
    vue(),  // 解析 Vue 单文件组件
    AutoImport({ resolvers: [ElementPlusResolver()] }),  // Element Plus 自动导入
    Components({ resolvers: [ElementPlusResolver()] }),
  ],
  test: {
    environment: 'happy-dom',  // 模拟浏览器环境
    include: ['src/**/*.test.ts'],  // 测试文件匹配规则
    setupFiles: ['../../test-setup.ts'],  // 全局设置（引入 jest-dom）
    css: false,  // 禁用 CSS 处理
    coverage: {
      provider: 'v8',
      thresholds: { lines: 50 },  // 覆盖率门槛
      exclude: ['src/main.ts', 'src/App.vue', 'src/router/**'],  // 排除非业务代码
    },
  },
})
```

#### node vs happy-dom 环境

| 环境 | 用途 | 例子 |
|------|------|------|
| `node` | 纯 TypeScript 工具库（没有 DOM 操作） | shared 包的 format.ts、validate.ts |
| `happy-dom` | Vue 组件测试（需要模拟浏览器） | web-user 的 ProductCard.vue |

#### 运行测试

```powershell

```

#### 监听模式（开发时推荐）


### 4.4 写一个测试用例

#### 测试工具函数（shared 包示例）

文件：`packages/shared/src/utils/format.test.ts`

```typescript
import { describe, it, expect } from 'vitest'
import { formatPrice } from './format'

// describe：一组相关测试
describe('formatPrice', () => {
  // it：一个测试用例
  it('应该把分转成元，保留两位小数', () => {
    // expect：断言（判断结果是否符合预期）
    expect(formatPrice(1999)).toBe('19.99')
  })

  it('应该处理 0 值', () => {
    expect(formatPrice(0)).toBe('0.00')
  })
})
```

#### 测试 Vue 组件（web-user 示例）

文件：`packages/web-user/src/components/ProductCard.test.ts`

```typescript
import { describe, it, expect } from 'vitest'
import { mount } from '@vue/test-utils'
import ProductCard from './ProductCard.vue'

describe('ProductCard', () => {
  it('应该显示商品名称', () => {
    const wrapper = mount(ProductCard, {
      props: {
        product: {
          id: 1,
          name: '测试商品',
          price: 1999,
          mainImage: 'test.jpg',
        },
      },
    })
    // 检查组件渲染的文本是否包含商品名称
    expect(wrapper.text()).toContain('测试商品')
  })

  it('点击应该触发 click 事件', async () => {
    const wrapper = mount(ProductCard, {
      props: { product: { id: 1, name: '测试', price: 100, mainImage: '' } },
    })
    await wrapper.trigger('click')
    expect(wrapper.emitted('click')).toBeTruthy()
  })
})
```

## 五、Playwright - 跨端 E2E 测试工具

### 5.1 这是什么？（小白版）

**Playwright = 剧作家**

简单说：让电脑像真人一样操作浏览器——打开网页、点击按钮、输入文字、截图，验证整个流程能不能走通。

#### 通俗类比

单元测试是检查"发动机零件对不对"，E2E 测试是"把车开上路跑一圈，看能不能到达目的地"。

#### 和单元测试的区别

| 维度 | 单元测试（Vitest） | E2E 测试（Playwright） |
|------|------------------|----------------------|
| 测试范围 | 单个函数/组件 | 整个用户流程（登录→下单→支付） |
| 速度 | 快（毫秒级） | 慢（秒级） |
| 稳定性 | 高（Mock 依赖） | 低（受网络/数据库影响） |
| 成本 | 低 | 高（环境搭建复杂） |
| 价值 | 发现代码 bug | 发现流程问题 |

### 5.5 写一个 E2E 测试

文件：`shop-frontend/e2e/user/auth.spec.ts`

```typescript
import { test, expect } from '@playwright/test'

// test.describe：一组相关测试
test.describe('用户登录', () => {
  // test：一个测试用例
  test('应该能用正确账号登录', async ({ page }) => {
    // 1. 打开登录页
    await page.goto('/login')

    // 2. 填写表单
    await page.fill('input[name="phone"]', '13800001111')
    await page.fill('input[name="password"]', '123456')

    // 3. 点击登录按钮
    await page.click('button[type="submit"]')

    // 4. 验证跳转到首页
    await expect(page).toHaveURL('/')

    // 5. 验证显示用户名
    await expect(page.locator('.user-name')).toContainText('张三')
  })

  test('密码错误应该提示', async ({ page }) => {
    await page.goto('/login')
    await page.fill('input[name="phone"]', '13800001111')
    await page.fill('input[name="password"]', 'wrongpassword')
    await page.click('button[type="submit"]')

    // 验证显示错误提示
    await expect(page.locator('.error-message')).toBeVisible()
  })
})
```

## 六、日常开发工作流

### 6.1 后端开发流程

```
1. 写代码（Java）
   ↓
2. 写单元测试（JUnit + Mockito）
   ↓
3. 本地运行测试
   mvn test -pl shop-order
   ↓
4. 查看覆盖率
   start shop-order/target/site/jacoco/index.html
   ↓
5. 覆盖率达标？
   ├─ 是 → 提交代码
   └─ 否 → 补测试用例 → 回到第 3 步
```

### 6.2 前端开发流程

```
1. 写代码（Vue/TypeScript）
   ↓
2. 写单元测试（Vitest）
   ↓
3. 本地运行测试（监听模式）
   npx vitest --watch
   ↓
4. 写 E2E 测试（Playwright，关键流程才写）
   ↓
5. 运行 E2E 测试
   npx playwright test --project=web-user
   ↓
6. 全部通过 → 提交代码
```

### 6.3 性能测试流程

```
1. 开发完成，准备上线
   ↓
2. 启动所有后端服务
   ↓
3. 准备测试数据
   .\perf\scripts\run-perf.ps1 -Scenario N-P-01 -SkipCleanup
   ↓
4. 运行性能测试
   .\perf\scripts\run-perf.ps1 -Scenario all
   ↓
5. 查看 HTML 报告
   start perf/results/N-P-01-report/index.html
   ↓
6. 指标达标？
   ├─ 是 → 清理测试数据 → 上线
   └─ 否 → 性能优化 → 回到第 4 步
```

## 七、常见问题

### Q1: mvn test 报 "Rule violated for bundle" 怎么办？

**原因**：覆盖率低于 60%，质量门禁拦截。

**解决**：
1. 打开 `shop-模块名/target/site/jacoco/index.html`
2. 找到红色（未覆盖）的类
3. 补充对应的单元测试
4. 重新 `mvn test`

### Q2: JMeter 报 "Not enough memory"

**解决**：编辑 `JMETER_HOME\bin\jmeter.bat`，增大堆内存：
```
set HEAP=-Xms1g -Xmx4g
```

### Q3: JMeter 测试错误率很高

**可能原因**：
- IP 限流触发（N-P-04/N-P-05）
- 测试数据未准备（N-P-03 秒杀库存未预热）
- 本机 IP 被拉黑（N-P-08 副作用）

**解决**：
```powershell
# 清理黑名单
docker exec shop-redis redis-cli DEL rate_limit:blacklist:ip

# 预热秒杀库存
docker exec shop-redis redis-cli SET seckill:stock:9999 100000
```

### Q4: Playwright 报 "browserType.launch: Executable doesn't exist"

**原因**：浏览器未安装。

**解决**：
```powershell
cd shop-frontend
npx playwright install chromium
```

### Q5: Playwright 测试不稳定，有时过有时不过（Flaky）

**原因**：E2E 测试受环境影响大，常见原因：
- 网络延迟导致等待超时
- 动画未完成就点击
- 异步数据未加载

**解决**：
- 用 `await page.waitForSelector('.element')` 等待元素出现
- 用 `await page.waitForTimeout(500)` 等待动画完成
- 配置 `retries: 2`（已配置，失败自动重试）

### Q6: Vitest 报 "Cannot find module '@shop/shared'"

**原因**：依赖未安装或别名未配置。

**解决**：
```powershell
cd shop-frontend
npm install
```

### Q7: 临时跳过质量门禁

```powershell
# 紧急发版时临时跳过（不要养成习惯）
mvn test -Djacoco.skip=true
```

### Q8: 如何查看历史性能测试结果

历史结果保存在 `perf/results/` 目录：

```powershell
# 查看所有历史报告
ls perf/results/

# 打开指定报告
start perf/results/N-P-01-report/index.html
```
