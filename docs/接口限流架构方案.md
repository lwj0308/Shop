# Shop 项目接口限流架构方案

> 基于电商高并发限流面试考点设计，构建四层纵深防御体系
> 生成时间：2026-07-04

---

## 一、背景与目标

### 1.1 为什么需要限流？

电商系统面临的高并发场景：

| 场景 | 流量特征 | 风险 |
|------|----------|------|
| 秒杀抢购 | 瞬时 QPS 暴涨 100 倍 | 超卖、数据库打挂、服务雪崩 |
| 登录注册 | 持续中频 + 爬虫攻击 | 密码爆破、短信轰炸 |
| 商品搜索 | 高 QPS 持续 | ES 压力大、响应慢 |
| 下单支付 | 中频但敏感 | 恶意占库存、重复提交 |
| 评论提交 | 低频但易刷 | 刷评水军 |

**核心目标**：保护后端资源、防止雪崩效应、保证大部分用户体验。

### 1.2 当前实现现状

| 层级 | 状态 | 算法 | 问题 |
|------|------|------|------|
| Gateway 网关层 | ✅ 已实现 | ZSet 精确滑动窗口 | 高频接口内存爆炸、无熔断能力 |
| 服务层 | ❌ 未实现 | - | Feign 调用无熔断，易雪崩 |
| 资源层 | ⚠️ 默认配置 | 连接池 | 未做针对性调优 |

### 1.3 升级目标

从"单层限流"升级为"四层纵深防御"，每层选最佳算法，实现 **限流 + 熔断 + 降级三位一体**。

## 二、限流算法选型分析（面试高频考点）

### 2.1 五种限流算法对比

| 算法 | 原理 | 精度 | 内存占用 | 突发流量 | 适用场景 | 实现难度 |
|------|------|------|----------|----------|----------|----------|
| **固定窗口** | 时间窗口内累加计数 | 低（有临界突发）| 极低 | ❌ | 粗粒度，如 IP 日限 | 简单 |
| **分格子滑动窗口** | 窗口切 N 格，滑动统计 | 中（格子越细越精确）| 低 | ❌ | 高频接口，Sentinel 默认 | 中等 |
| **ZSet 精确滑动窗口** | 记录每个请求时间戳 | 高（毫秒级）| 高（每请求一条）| ❌ | 低频高精度，如认证 5 QPS | 中等 |
| **漏桶** | 恒定速率出水 | 高（绝对平滑）| 低 | ❌ 不允许 | 整流保护下游，如 MQ 消费 | 中等 |
| **令牌桶** | 固定速率发令牌 | 高 | 低 | ✅ 允许合理突发 | API 网关入口，工业界最常用 | 中等 |

### 2.2 分格子滑动窗口 vs ZSet 精确滑动窗口

**这是面试常考的对比点，也是本项目算法选型的关键**。

```
分格子滑动窗口（Sentinel 默认实现）：
  1秒切 2 个 500ms 格子，只存 2 个计数
  内存：O(格子数)  →  极低
  性能：O(1)       →  极快
  精度：500ms 粒度 →  够用

ZSet 精确滑动窗口（当前 Gateway 实现）：
  每个请求存一条 ZSET 记录（member=请求ID, score=时间戳）
  内存：O(请求数)  →  50 QPS × 1秒 = 50 条记录/Key
  性能：O(log N)   →  ZADD/ZCARD 复杂度
  精度：毫秒级     →  最精确
```

**选型原则**：

| 场景 | 推荐算法 | 原因 |
|------|----------|------|
| 低频高精度（认证 5 QPS）| ZSet 精确滑动窗口 | 内存可接受，精度最高 |
| 高频接口（商品浏览 50+ QPS）| 令牌桶或分格子 | ZSet 内存爆炸，每秒 50 条记录 |
| API 网关入口 | 令牌桶 | 允许合理突发，工业界标准 |
| 服务内部方法 | 分格子滑动窗口（Sentinel）| 性能好，自带熔断 |
| 整流保护下游 | 漏桶 | 绝对平滑，如 MQ 消费速率 |

### 2.3 限流 + 熔断 + 降级 三位一体

**面试核心考点：三者缺一不可**

| 防线 | 触发条件 | 响应时间 | 职责 | 项目应用 |
|------|----------|----------|------|----------|
| **限流** | QPS 超阈值 | <1ms | 控制进入流量 | Gateway IP/接口限流 |
| **熔断** | 错误率>50% / 慢调用>50% | <1ms（快速失败）| 切断故障链路 | Feign 调用熔断 |
| **降级** | 熔断触发 / 业务异常 | <10ms | 返回兜底数据 | 返回缓存/默认值 |

```
请求进入
   ↓
┌─ 限流（Gateway + Sentinel）→ 超限返回 429
│   ↓ 放行
├─ 熔断（Sentinel 熔断器）→ 下游异常时快速失败
│   ↓ 正常
├─ 业务执行
│   ↓ 失败
└─ 降级（Fallback）→ 返回兜底数据/缓存/默认值
```

## 三、四层限流架构设计

### 3.1 整体架构

```
┌──────────────────────────────────────────────────────────────────┐
│  第1层：Nginx 接入层（可选，当前未部署 Nginx）                    │
│  算法：固定窗口（limit_req 模块）                                 │
│  限流维度：IP                                                     │
│  职责：防 DDoS、爬虫，挡掉最暴力的流量                            │
│  状态：⏸ 可选（后期部署 Nginx 时启用）                            │
└────────────────────────────┬─────────────────────────────────────┘
                             ↓
┌──────────────────────────────────────────────────────────────────┐
│  第2层：Gateway 网关层                                            │
│  算法：令牌桶（Redis + Lua）+ ZSet 精确滑动窗口（低频接口保留）   │
│  限流维度：IP + 接口                                              │
│  职责：外部入口限流，允许合理突发，分级规则                       │
│  状态：🔄 需优化（高频接口 ZSet → 令牌桶）                        │
└────────────────────────────┬─────────────────────────────────────┘
                             ↓
┌──────────────────────────────────────────────────────────────────┐
│  第3层：服务层（Sentinel）⭐ 核心补充                             │
│  算法：分格子滑动窗口（Sentinel 默认，1秒2格500ms）               │
│  限流维度：方法/资源 + Feign 调用                                 │
│  职责：方法级细粒度限流 + 熔断降级 + 集群流控                     │
│  状态：❌ 待实施                                                  │
│  重点保护：                                                       │
│    - shop-product: StockService.deduct（库存扣减）               │
│    - shop-order: OrderService.createOrder（下单）                │
│    - shop-seckill: SeckillService.grab（秒杀抢购）               │
│    - Feign 调用：shop-order → shop-product（熔断防雪崩）         │
└────────────────────────────┬─────────────────────────────────────┘
                             ↓
┌──────────────────────────────────────────────────────────────────┐
│  第4层：资源层（兜底防线）                                        │
│  - MySQL 连接池上限（HikariCP maximumPoolSize）                  │
│  - Redis 连接池上限（Lettuce max-active）                        │
│  - Tomcat/Netty 线程池上限                                       │
│  职责：最后防线，防止资源耗尽                                     │
│  状态：⚠️ 需调优                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 3.2 各层职责划分

| 层级 | 限流对象 | 限流维度 | 算法 | 优势 | 劣势 |
|------|----------|----------|------|------|------|
| Nginx | 外部流量 | IP | 固定窗口 | 性能极高 | 粗粒度 |
| Gateway | 外部请求 | IP/接口 | 令牌桶 + ZSet | 集中管理、多实例共享 | 无法熔断 |
| 服务层 | 内部方法 | 方法/资源 | 分格子滑动窗口 | 细粒度、熔断降级 | 新依赖 |
| 资源层 | 系统资源 | 连接/线程 | 池化 | 兜底防线 | 治标不治本 |

### 3.3 三层防护协作流程（以秒杀为例）

```
用户抢购
   ↓
第1层 Gateway 限流（IP 3 QPS）
   ├─ 超限 → 返回 429"请求太频繁"
   └─ 放行 ↓
第2层 Sentinel 限流（方法 1000 QPS）
   ├─ 超限 → 返回 429"当前访问人数较多"
   └─ 放行 ↓
第3层 Redis Lua 库存扣减（原子操作）
   ├─ 库存不足 → 返回"已抢完"
   └─ 扣减成功 ↓
异步创建订单（MQ）
   └─ 返回"抢购成功，正在处理"
```

## 四、各层方案详细设计

### 4.1 第2层：Gateway 层优化（令牌桶替换 ZSet）

#### 4.1.1 为什么要换？

当前 ZSet 精确滑动窗口的问题：
- 每个请求存一条 ZSET 记录，50 QPS × 1000 接口 = 每秒 5 万条记录
- ZADD/ZCARD 是 O(log N) 操作，高并发下 Redis CPU 飙升
- 内存浪费严重（记录时间戳 + 成员）

令牌桶优势：
- 只存 2 个字段（剩余令牌数 + 上次补充时间），内存 O(1)
- 允许合理突发（如配置 50 QPS，桶容量 100，可瞬时处理 100 请求）
- 工业界 API 网关标准方案（Guava RateLimiter、Nginx limit_req 都是令牌桶变种）

#### 4.1.2 令牌桶算法原理

```
参数：
  rate     = 令牌生成速率（令牌/秒）
  capacity = 桶容量（最大突发量）

状态（Redis 存储）：
  tokens       = 当前剩余令牌数
  last_refill  = 上次补充时间戳

每次请求：
  1. 计算时间差 Δt = now - last_refill
  2. 补充令牌：tokens = min(capacity, tokens + Δt × rate)
  3. 判断：
     - tokens >= 1 → 消耗 1 令牌，放行
     - tokens < 1  → 拒绝（429）
  4. 更新 tokens 和 last_refill
```

#### 4.1.3 分级配置

| 接口类型 | 速率（令牌/秒）| 桶容量（突发）| 算法选择 | 说明 |
|----------|----------------|----------------|----------|------|
| 认证接口 | 5 | 10 | ZSet 精确滑动窗口 | 低频高精度，保留现有实现 |
| 秒杀抢购 | 3 | 5 | 令牌桶 | 严格防刷单 |
| 下单支付 | 10 | 20 | 令牌桶 | 允许短时突发 |
| 评论提交 | 3 | 5 | ZSet 精确滑动窗口 | 低频高精度 |
| 商品浏览 | 50 | 100 | 令牌桶 | 允许合理突发 |
| 默认 | 50 | 100 | 令牌桶 | 兜底 |

#### 4.1.4 实现要点

- Lua 脚本保证原子性（补充令牌 + 消耗令牌在 Redis 单线程内完成）
- 降级策略：Redis 异常时放行（限流是弱依赖）
- 配置热更新：Nacos 配置，修改后立即生效

#### 4.1.5 Redis 分布式限流生产级细节（后期集群部署必读）

> ⚠️ 当前为本地 Docker 单节点 Redis，以下细节在后期上集群时必须处理。

**1. 集群哈希槽兼容（Redis Cluster）**

Redis Cluster 采用哈希槽分片，Lua 脚本要求所有 Key 必须落在同一哈希槽，否则报错 `CROSSSLOT`。

**解决方案**：用 hashtag（花括号）强制同业务 Key 落同一槽。

```
原始 Key（集群下会报错）：
  rate_limit:ip:1.2.3.4
  rate_limit:path:/api/order

加 hashtag（同一业务前缀，落同一槽）：
  {rate_limit}:ip:1.2.3.4
  {rate_limit}:path:/api/order
```

⚠️ 注意：hashtag 会把所有限流 Key 集中到一个节点，可能造成热点。生产环境建议按业务拆分 hashtag：
- `{rate_limit:ip}:1.2.3.4`
- `{rate_limit:user}:1001`
- `{rate_limit:path}:/api/order`

**2. ZSet 成员唯一性**

ZSet 精确滑动窗口中，`member` 必须全局唯一，否则同毫秒请求会覆盖，导致计数偏少、限流失效。

**错误做法**：
```lua
-- 用时间戳做 member，同毫秒请求会覆盖
redis.call('ZADD', key, now, tostring(now))
```

**正确做法**：
```lua
-- 用 UUID + 纳秒做 member，保证唯一
local uid = ARGV[4]  -- Java 传入的 UUID
redis.call('ZADD', key, now, uid)
```

Java 端生成唯一 ID：
```java
// 推荐：UUID（足够唯一，性能好）
String requestId = UUID.randomUUID().toString();

// 高性能场景：雪花 ID
// String requestId = SnowflakeIdGenerator.nextId();
```

**3. 大窗口内存优化**

分钟级、小时级大窗口的 ZSet 限流，请求记录堆积会占用大量内存。

| 窗口大小 | 50 QPS 内存估算 | 问题 |
|----------|----------------|------|
| 1 秒 | 50 条/Key | 可接受 |
| 1 分钟 | 3000 条/Key | 内存压力大 |
| 1 小时 | 18 万条/Key | 内存爆炸 |

**优化方案**：

| 窗口大小 | 推荐算法 | 原因 |
|----------|----------|------|
| ≤1 秒 | ZSet 精确滑动窗口 | 精度高，内存可接受 |
| 1 秒 ~ 1 分钟 | 分格子滑动窗口 | 内存低，精度够用 |
| ≥1 分钟 | 固定窗口（计数器）| 粗粒度即可，内存极低 |

**大窗口分格子实现**：
```
1 分钟窗口，切 6 个 10 秒格子
  格子 0：[0-10s)   计数 8
  格子 1：[10-20s)  计数 12
  格子 2：[20-30s)  计数 5
  ...
  格子 5：[50-60s)  计数 10

总计数 = 8+12+5+...+10 = 60
内存：仅 6 个数字，远低于 ZSet 的 60 条记录
```

**4. 冷 Key 清理**

限流 Key 在无请求时应自动过期，避免内存浪费。

```lua
-- Lua 脚本最后设置过期时间
redis.call('PEXPIRE', key, window + 1000)  -- 窗口 + 1 秒缓冲
```

**5. 当前单节点 vs 后期集群的差异**

| 维度 | 单节点（当前）| 集群（后期）|
|------|--------------|-------------|
| Key 设计 | 普通 Key 即可 | 必须加 hashtag |
| Lua 脚本 | 无限制 | 所有 Key 同槽 |
| 限流精度 | 全局精确 | 同槽内精确 |
| 性能 | 受单节点限制 | 可扩展 |
| 部署复杂度 | 低 | 高 |

### 4.2 第3层：服务层 Sentinel（核心补充）

#### 4.2.1 为什么需要 Sentinel？Gateway 限流不够吗？

**场景**：shop-order 调用 shop-product 扣库存，shop-product 宕机
- Gateway 限流：无能为力（请求已经进入服务内部）
- Sentinel 熔断：检测到 shop-product 错误率 > 50%，5 秒内快速失败，不拖垮 shop-order

**Gateway 限流 vs Sentinel 限流对比**：

| 维度 | Gateway 限流 | Sentinel 限流 |
|------|--------------|---------------|
| 位置 | 网关入口 | 服务内部方法 |
| 限流对象 | 外部请求 | 内部方法/Feign 调用 |
| 限流维度 | IP/接口 | 方法/QPS/调用关系 |
| 熔断降级 | ❌ 不支持 | ✅ 支持（错误率/慢调用）|
| 规则推送 | Nacos 配置 | Sentinel Dashboard |
| 适用场景 | 防外部刷 | 防内部雪崩 |

#### 4.2.2 Sentinel 三大能力

| 能力 | 作用 | 项目应用 |
|------|------|----------|
| **限流** | 方法级 QPS 控制 | StockService.deduct 限 1000 QPS |
| **熔断** | 错误率/慢调用触发断路 | Feign 调用 shop-product 失败时熔断 |
| **降级** | 返回兜底数据 | 商品详情查不到时返回缓存数据 |

#### 4.2.3 熔断器状态机

```
         错误率>50% / 慢调用>50%
    ┌─────────────────────────────┐
    │                             ↓
┌───┴────┐    熔断超时    ┌────────┴───┐    探测成功    ┌───┬────┐
│ Closed │ ───────────→ │ Half-Open │ ───────────→ │ Closed │
│ (正常)  │              │ (探测中)   │              │ (恢复)  │
└────────┘              └────────────┘              └────────┘
    ↑                         │
    │                         │ 探测失败
    │                         ↓
    │                    ┌────────┐
    └────────────────────│  Open  │
         熔断超时         │ (熔断)  │
                         └────────┘
```

#### 4.2.4 重点项目场景

**场景 1：秒杀抢购（shop-seckill）**
```
Gateway 限流（IP 3 QPS）
  → Sentinel 限流（方法 1000 QPS）
    → Redis Lua 库存扣减
三层防护，每层职责清晰
```

**场景 2：下单链路（shop-order → shop-product）**
```
shop-order 调用 shop-product 扣库存
Sentinel 熔断：shop-product 错误率 > 50%
  → 5 秒内快速失败
    → 触发降级（回滚订单 + 提示"系统繁忙"）
```

**场景 3：商品详情（shop-product）**
```
Sentinel 降级策略：
  数据库查不到 → 返回 Redis 缓存
    → 缓存也没有 → 返回默认商品信息
```

#### 4.2.5 集群流控（高级，可选）

| 模式 | 说明 | 适用场景 |
|------|------|----------|
| 单机限流 | 每个实例独立限流 | 实例数少，精度要求不高 |
| 集群限流 | Token Server 统一发放令牌 | 实例数多，需精确全集群控制 |

**单机 vs 集群**：
- 单机限流：每个实例 1000 QPS，5 个实例 = 5000 QPS（可能超总量）
- 集群限流：全集群精确控制 2000 QPS

#### 4.2.6 自适应限流（系统级保护）

固定阈值限流在流量波动时存在僵化问题：阈值设高了，系统压力小但保护不足；阈值设低了，系统资源闲置但用户被拒。Sentinel 自带系统自适应限流，根据系统实时指标动态调整阈值。

**为什么需要自适应限流？**

电商大促场景流量特征：
```
平时 QPS：500       → 固定阈值 1000 足够
大促 QPS：5000      → 固定阈值 1000 会误杀，固定阈值 5000 平时浪费
```

自适应限流根据系统负载动态调整：
- 流量平稳时：放宽阈值，充分利用资源
- 流量突增时：收紧阈值，保障系统可用性

**Sentinel 系统规则（SystemRule）**：

| 指标 | 说明 | 建议阈值 |
|------|------|----------|
| **CPU 使用率** | 系统级 CPU 占用 | >75% 触发限流 |
| **系统负载（Load）** | 系统平均负载 | >2 × CPU 核数触发 |
| **平均 RT** | 所有接口平均响应时间 | >10ms 触发 |
| **入口 QPS** | 所有入口总 QPS | >系统压测阈值触发 |
| **线程数** | 所有入口总线程数 | >100 触发 |

**配置示例**：
```java
@PostConstruct
public void initSystemRule() {
    SystemRule rule = new SystemRule();
    rule.setHighestCpuUsage(0.75);     // CPU 使用率 > 75% 触发
    rule.setHighestSystemLoad(4.0);    // 系统负载 > 4 触发（2核CPU建议4）
    rule.setAvgRt(10);                 // 平均响应时间 > 10ms 触发
    rule.setQps(2000);                 // 入口总 QPS > 2000 触发
    rule.setMaxThread(100);            // 入口总线程数 > 100 触发
    SystemRuleManager.loadRules(Collections.singletonList(rule));
}
```

**自适应限流 vs 固定限流**：

| 维度 | 固定限流 | 自适应限流 |
|------|----------|------------|
| 阈值 | 配置写死 | 根据系统指标动态调整 |
| 适用场景 | 接口级精确控制 | 系统级兜底保护 |
| 响应速度 | 即时 | 滞后（需采集指标）|
| 误杀率 | 高（流量波动时）| 低（自动调整）|

**项目应用建议**：
- 接口级限流：用固定 QPS 限流（如秒杀 3 QPS）
- 系统级兜底：用自适应限流（CPU > 75% 全局限流）
- 两者配合：固定限流做精细控制，自适应限流做兜底保护

**适用服务**：
- shop-product（商品服务，流量大）
- shop-order（订单服务，资源敏感）
- shop-seckill（秒杀服务，突发流量）
- shop-gateway（网关入口，全局兜底）

### 4.3 第4层：资源层兜底

| 资源 | 当前配置 | 建议配置 | 说明 |
|------|----------|----------|------|
| HikariCP（MySQL）| 默认 10 | maximumPoolSize=20 | 防止连接打满 |

### 4.4 限流维度设计详解（电商场景核心）

电商场景下，单纯 IP 维度限流存在盲区：羊毛党切换 IP 即可绕过。需要补充用户维度、热点商品维度、黑白名单机制。

#### 4.4.1 限流维度对比

| 维度 | 限流 Key | 适用场景 | 优势 | 劣势 |
|------|----------|----------|------|------|
| **IP 维度** | `rate_limit:ip:{ip}` | 匿名接口、登录前请求 | 防爬虫、实现简单 | 代理 IP 可绕过 |
| **用户维度** | `rate_limit:user:{userId}` | 登录态接口（下单/秒杀/领券）| 防刷单、羊毛党 | 需登录态 |
| **接口维度** | `rate_limit:path:{path}` | 所有接口 | 保护后端服务 | 粒度较粗 |
| **热点商品维度** | `rate_limit:product:{productId}` | 爆款商品详情/库存 | 防单点打垮 | 需识别热点 |
| **方法维度** | Sentinel 资源名 | 服务内部方法 | 细粒度 | 仅服务层 |

#### 4.4.2 用户维度限流（核心补充）

**为什么需要用户维度？** 电商刷单、羊毛党通常切换 IP 绕过 IP 限流，但用户 ID 无法伪造。

**适用接口**：登录态接口（下单、秒杀、领券、评论、支付）

**实现方式**：
- Gateway 层：从 Token 解析 `userId`，作为限流 Key
- 未登录请求：降级用 IP 维度限流

**Key 设计**：
```
登录用户：rate_limit:user:1001    （用户ID=1001）
未登录：  rate_limit:ip:1.2.3.4   （降级用IP）
```

**分级配置建议**：

| 接口类型 | 用户 QPS | 说明 |
|----------|----------|------|
| 秒杀抢购 | 3 | 严格防刷单 |
| 领券 | 5 | 防羊毛党 |
| 下单 | 10 | 防恶意占库存 |
| 评论提交 | 3 | 防刷评 |
| 默认 | 20 | 兜底 |

#### 4.4.3 热点商品维度限流

**场景**：爆款商品（如 iPhone 新品）详情页 QPS 可能是普通商品的 100 倍，单点打垮整个商品服务。

**实现方式**：Sentinel 热点参数限流（`ParamFlowRule`）

```java
@SentinelResource(value = "product:detail")
public ProductDetailVO getProductDetail(@RequestParam Long productId) {
    // 业务逻辑
}
```

```java
// 热点参数限流规则：针对 productId 维度
ParamFlowRule rule = new ParamFlowRule("product:detail")
    .setParamIdx(0)              // 第0个参数（productId）
    .setGrade(RuleConstant.FLOW_GRADE_QPS)
    .setCount(500);              // 单个商品 500 QPS

// 特例：爆款商品单独配置更高阈值
ParamFlowItem item = new ParamFlowItem();
item.setObject("10086");         // 商品ID=10086
item.setClassType(String.class.getName());
item.setCount(2000);             // 爆款商品 2000 QPS
rule.setParamFlowItemList(List.of(item));
```

**热点商品识别**：
- 运营预配置：大促前手动标记爆款商品
- 自动识别：Redis ZSET 统计商品访问量，Top N 自动加入热点规则

#### 4.4.4 黑白名单机制

**比限流更高效**：黑名单直接拦截，不消耗限流配额；白名单直接放行，不受限流约束。

| 名单类型 | 存储结构 | Key 设计 | 生效层级 |
|----------|----------|----------|----------|
| IP 白名单 | Redis Set | `whitelist:ip` | Gateway |
| IP 黑名单 | Redis Set | `blacklist:ip` | Gateway |
| 用户白名单 | Redis Set | `whitelist:user` | Gateway + 服务层 |
| 用户黑名单 | Redis Set | `blacklist:user` | Gateway + 服务层 |

**Gateway 过滤器执行顺序**：
```
请求进入
  ↓
黑名单检查 → 命中黑名单 → 直接 403（不做友好提示）
  ↓ 未命中
白名单检查 → 命中白名单 → 跳过限流，直接放行
  ↓ 未命中
限流检查（IP/用户/接口维度）
  ↓ 通过
鉴权 + 转发
```

**黑名单自动拉黑策略**：
- 触发限流超过 N 次 → 自动拉黑 1 小时
- 恶意请求特征（如 SQL 注入尝试）→ 永久拉黑
- 风控系统判定 → 手动拉黑

**白名单场景**：
- 内部服务 IP（Feign 调用不走限流）
- 运维节点 IP（监控、巡检）
- VIP 用户（VIP 通道不受限流约束）
- 内部测试账号

### 4.5 限流与业务幂等的配合（电商核心）

电商核心接口（下单、支付、库存扣减）不仅需要限流，还需要幂等保障。限流和幂等必须联动，否则会出现限流重试导致的重复提交、超卖等问题。

#### 4.5.1 为什么需要联动？

**问题场景**：
```
用户下单 → 限流拒绝（429）→ 用户重试 → 限流放行 → 重复下单？
                                   ↓
                            幂等键相同 → 服务端去重 → 返回首次结果
```

如果不联动：
- 限流拒绝的请求可能已经消耗了幂等键 → 重试时幂等键变了 → 重复下单
- 限流放行的请求没有幂等键 → 网络超时用户重试 → 重复扣库存

#### 4.5.2 联动设计

**原则**：限流拒绝的请求不消耗幂等键；限流放行的请求必须携带幂等键。

**幂等键生成规则**：
- 客户端生成：`业务类型 + 用户ID + 时间戳 + 随机数`（如 `order_1001_1783168744_abc123`）
- 服务端校验：Redis SETNX 判断幂等键是否已存在

**联动流程**：
```
客户端请求（携带幂等键 idempotentKey）
  ↓
Gateway 限流检查
  ├─ 限流拒绝 → 直接返回 429（不消耗幂等键，客户端可用相同 key 重试）
  └─ 限流通过 ↓
服务端幂等检查（Redis SETNX idempotentKey）
  ├─ 幂等键已存在 → 返回首次处理结果（重复请求）
  └─ 幂等键不存在 ↓
业务处理 + 持久化幂等键（带 TTL，如 24 小时）
```

**关键点**：
- 幂等检查在限流之后：避免被限流的请求消耗幂等键
- 幂等键 TTL 设置：覆盖业务最大处理时间 + 重试窗口（建议 24 小时）
- 幂等键存储：Redis SETNX，保证原子性

**项目应用**：

| 接口 | 幂等键格式 | TTL | 说明 |
|------|------------|-----|------|
| 下单 | `order:{userId}:{clientToken}` | 24h | 防重复下单 |
| 支付 | `pay:{orderId}:{requestId}` | 2h | 防重复扣款 |
| 库存扣减 | `stock:{orderNo}:{skuId}` | 24h | 防超卖 |
| 秒杀抢购 | `seckill:{userId}:{seckillId}` | 1h | 防重复抢购 |
| 领券 | `coupon:{userId}:{couponId}` | 1h | 防重复领券 |

### 4.6 限流后处理策略（精细化）

当前方案默认限流返回 429，电商场景应做更精细化的处理，提升用户体验。

#### 4.6.1 分场景处理策略

| 场景 | 处理方式 | 响应内容 | HTTP 状态码 |
|------|----------|----------|-------------|
| **普通浏览接口** | 友好提示 + 缓存兜底 | "当前访问人数较多，显示缓存数据" | 200（带缓存标识）|
| **秒杀/活动接口** | 排队机制（异步处理）| "正在排队中，请稍候" + 排队号 | 202（Accepted）|
| **登录态业务接口** | 友好提示 + 重试建议 | "操作太频繁，请稍后重试" | 429 |
| **恶意流量** | 直接拒绝 + 拉黑 | 错误页 / 空 response | 403 |
| **内部 Feign 调用** | 快速失败 + 降级 | Fallback 兜底数据 | 200（降级数据）|

#### 4.6.2 秒杀排队机制（重点）

秒杀场景直接返回 429 体验差，改为"排队机制"：

```
用户抢购
  ↓
Gateway 限流（IP 3 QPS）
  ├─ 超限 → 返回 202"排队中" + 排队号
  └─ 通过 ↓
Sentinel 限流（方法 1000 QPS）
  ├─ 超限 → 返回 202"排队中" + 排队号
  └─ 通过 ↓
Redis Lua 库存扣减
  ├─ 库存不足 → 返回"已抢完"
  └─ 扣减成功 ↓
异步创建订单（MQ）→ 返回"抢购成功，正在处理"
```

**排队机制实现**：
- 超限请求生成排队号，写入 Redis 队列
- 前端轮询排队状态（或 WebSocket 推送）
- 后端按处理能力消费队列，避免直接拒绝

**前端体验**：
```
点击"立即抢购"
  ↓
显示"排队中...（前方还有 N 人）"
  ↓
轮询结果
  ├─ 抢购成功 → 跳转订单页
  ├─ 已抢完 → 提示"已抢完"
  └─ 排队超时（30秒）→ 提示"系统繁忙，请重试"
```

#### 4.6.3 浏览接口缓存兜底

商品列表、搜索等浏览接口限流时，返回缓存数据而非错误页：

```java
@SentinelResource(value = "product:list", blockHandler = "listBlockHandler")
public Result listProducts(ProductQueryDTO query) {
    // 正常查询
}

public Result listBlockHandler(ProductQueryDTO query, BlockException ex) {
    // 限流时返回缓存数据
    String cacheKey = "product:list:cache:" + query.hashCode();
    Object cached = redisTemplate.opsForValue().get(cacheKey);
    if (cached != null) {
        return Result.success(cached).setMessage("当前访问人数较多，显示缓存数据");
    }
    // 缓存也没有，返回默认推荐
    return Result.success(getDefaultRecommend()).setMessage("当前访问人数较多");
}
```

## 七、风险与降级策略

### 7.1 限流组件故障的降级

| 故障场景 | 降级策略 | 理由 |
|----------|----------|------|
| Redis 宕机 | Gateway 限流放行 | 限流是弱依赖，不阻断主流程 |
| Sentinel 宕机 | 服务限流放行 | Sentinel 是弱依赖，业务正常执行 |
| Nacos 宕机 | 使用本地缓存规则 | 规则已缓存到本地 |

### 7.2 限流阈值设置原则

- **先压测后设置**：通过 JMeter 压测确定系统承受能力
- **留 30% 余量**：如系统最大 1000 QPS，限流设 700 QPS
- **分级设置**：核心接口严格，非核心接口宽松
- **动态调整**：大促前临时调高，平时调低

### 7.3 监控告警

| 指标 | 阈值 | 告警方式 |
|------|------|----------|
| 限流触发率 | >10% | 企微/钉钉告警 |
| 熔断触发次数 | >0 | 立即告警 |
| 接口响应时间 | P99 > 1s | 告警 |
| Redis CPU | >80% | 告警 |
