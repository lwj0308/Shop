# Shop 项目接口幂等性架构方案

> 基于"注解化 + 分级防护"的统一幂等体系，覆盖资金、状态变更、内部调用全链路
> 初版时间：2026-07-08 | 更新时间：2026-07-10（落地完成）

---

## 一、背景与目标

### 1.1 为什么需要接口幂等性？

电商系统的写操作（下单、支付、退款等）面临四类重复请求风险：

| 风险场景 | 触发原因 | 业务后果 |
|----------|----------|----------|
| 用户重复点击 | 网络卡顿、按钮没禁用 | 重复下单、重复扣款 |
| 网络重试 | 超时后客户端自动重试、Feign 重试 | 重复扣库存、重复核销券 |
| 回调重发 | 第三方支付平台重复回调 | 重复更新订单状态、重复发货 |
| MQ 重复消费 | RocketMQ At-Least-Once 语义 | 重复创建秒杀订单 |

**核心目标**：保证同一业务请求无论被提交多少次，业务结果只有一个。

### 1.2 升级前 vs 升级后

| 维度 | 升级前 | 升级后 |
|------|--------|--------|
| 注解使用 | `@Idempotent` 功能完整但**零使用** | 13 个接口全部接入 |
| 下单幂等 | 手写 `checkIdempotentToken` + `@RequestHeader` | `@Idempotent` 注解，移除手写代码 |
| 秒杀幂等 | 手写 Lua 脚本，key 前缀 `seckill:grab:lock:` | 保留 Lua 脚本，key 前缀统一 `idempotent:seckill:grab:` |
| 支付幂等 | 仅回调有分布式锁+状态+唯一索引 | 创建/回调/退款全覆盖 |
| 取消/确认/发货 | ❌ 无防护 | `@Idempotent` SpEL 策略 |
| 评论/领券 | ❌ 无防护 | `@Idempotent` 注解 |
| 内部 Feign | ❌ 无防护 | `@Idempotent` SpEL 策略防重试 |
| Key 命名 | 各接口自定义，不统一 | 统一 `idempotent:{服务}:{业务}:{key}` |
| 前端配合 | 全量注入 Header（会覆盖 SpEL 策略） | 白名单注入，仅 Header 策略接口传 Key |

## 二、幂等性原理与策略

### 2.1 四种主流幂等方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| **SETNX** | Redis SETNX 占用 key，重复请求拒绝 | 实现简单、性能高、通用 | 需要选 key、TTL | 大多数写接口 |
| **Token 令牌** | 前端先获取 Token，提交时验证并删除 | 安全性高、无 TTL 困扰 | 需要额外接口、时序依赖强 | 表单提交、敏感操作 |
| **状态机** | 依赖数据库状态字段判断是否已处理 | 强一致、无需 Redis | 仅适合有状态的业务 | 订单状态、支付状态 |
| **唯一索引** | 数据库唯一约束兜底 | 最终一致、防重绝对 | 只能兜底、报错处理复杂 | 回调日志、订单号 |

### 2.2 本项目选型策略

```
对外接口（用户端）— Header 策略：
  @Idempotent 注解 + 前端 X-Idempotent-Key Header
  适用：下单、支付创建、评论（前端生成唯一键）

对外接口（用户端）— SpEL 策略：
  @Idempotent(key="#id") 注解 + 业务参数提取 key
  适用：取消订单、确认收货、发货、领券（按资源 ID 幂等）

内部接口（Feign）— SpEL 策略：
  @Idempotent(key="#orderNo") 注解 + 业务参数提取 key
  适用：库存扣减、券核销、券回退（防 Feign 重试）

特殊场景（秒杀）— 手写 Lua 脚本：
  保留手写逻辑（库存扣减与幂等原子绑定，无法拆分）
  原因：秒杀的"防重复点击"和"扣库存"必须原子执行，否则会超卖

最终兜底 — 数据库：
  唯一索引 + 状态机校验
  适用：支付回调（out_trade_no 唯一索引 + 支付状态校验）
```

### 2.3 幂等键解析优先级（@Idempotent 注解）

```
1. Header（X-Idempotent-Key）：Header 策略接口使用，前端自动生成
       ↓ 为空时回退
2. SpEL 表达式：SpEL 策略接口使用，从业务参数提取（如 #id、#dto.orderNo）
       ↓ 为空时回退
3. 自动生成：className.methodName:userId:argsHash
       兜底策略，确保总有 key
```

> **关键设计**：Header 优先级最高。前端仅对 Header 策略接口注入 X-Idempotent-Key，
> 避免覆盖 SpEL 策略接口的业务级幂等键（详见第六章前端配合）。

## 三、已实现接口清单

### 3.1 分级标准

| 级别 | 含义 | 降级策略 | 适用接口 |
|------|------|----------|----------|
| **P0** | 资金类，必须幂等 | Redis 异常时**降级放行**（幂等是防护） | 下单、支付、退款、秒杀 |
| **P1** | 状态变更类，建议幂等 | Redis 异常时降级放行 | 取消、确认、发货、评论、领券 |
| **P2** | 内部调用类，防重调用 | Redis 异常时降级放行 | 库存扣减、券核销、券回退 |

> **注意**：秒杀是例外。秒杀的 Redis 库存是**强依赖**（超卖比拒绝对业务伤害更大），不降级。

### 3.2 P0 资金类（5 个接口）

| 接口 | 方法 | 策略 | 幂等键来源 | Key 前缀 | TTL | 实现方式 |
|------|------|------|------------|----------|-----|----------|
| `POST /order` 创建订单 | POST | Header | X-Idempotent-Key | `idempotent:order:create:` | 300s | @Idempotent 注解 |
| `POST /payment/create` 创建支付 | POST | Header | X-Idempotent-Key | `idempotent:payment:create:` | 300s | @Idempotent 注解 |
| `POST /payment/callback` 支付回调 | POST | SpEL | `#dto.paymentNo` | `idempotent:payment:callback:` | 600s | @Idempotent + 分布式锁 + 状态 + 唯一索引 |
| `POST /payment/refund` 退款 | POST | SpEL | `#paymentId` | `idempotent:payment:refund:` | 300s | @Idempotent 注解 |
| `POST /order/seckill/{id}` 秒杀抢购 | POST | 手写 Lua | seckillId+userId | `idempotent:seckill:grab:` | 5s | Lua 脚本原子扣库存 |

### 3.3 P1 状态变更类（5 个接口）

| 接口 | 方法 | 策略 | 幂等键来源 | Key 前缀 | TTL | 实现方式 |
|------|------|------|------------|----------|-----|----------|

| `POST /user/coupon/receive/{id}` 领券 | POST | SpEL | `#couponId` | `idempotent:coupon:receive:` | 60s | @Idempotent 注解 |

## 四、Redis Key 规范

### 4.1 命名规范

```
格式：idempotent:{服务名}:{业务标识}:{幂等键}
```

**示例**：
```
idempotent:order:create:order_a1b2c3d4_1700000000000_abc12345
idempotent:payment:callback:PAY202607080001
idempotent:product:deduct:ORD202607080001
idempotent:seckill:grab:10086:1001
```

### 4.2 TTL 策略

| 业务类型 | TTL | 原因 |
|----------|-----|------|
| 下单 | 300s（5分钟） | 覆盖订单创建全流程，防止超时重试 |
| 支付创建 | 300s | 防止重复创建支付单 |
| 支付回调 | 600s（10分钟） | 第三方可能延迟重发回调 |
| 退款 | 300s | 防止重复退款 |
| 秒杀抢购 | 5s | 短时防重复点击，不影响二次抢购 |
| 状态变更 | 60s | 短时防误操作 |
| 内部调用 | 300s | 覆盖 Feign 重试窗口 |

### 4.3 异常回滚策略

| 场景 | 处理方式 | 原因 |
|------|----------|------|
| 业务方法正常返回 | Key 自然过期 | 不删除，防止成功后重试 |
| 业务方法抛 BusinessException | 删除 Key，允许重试 | 业务失败应允许重试 |
| 业务方法抛其他异常 | 删除 Key，允许重试 | 系统异常应允许重试 |
| Redis SETNX 异常 | 降级放行 | 幂等是防护，不阻断业务 |
| Redis 删除 Key 异常 | 仅记录日志 | 不影响主流程 |

## 五、核心亮点

### 5.1 注解化统一——一次开发，处处复用

```
@Idempotent(prefix = "idempotent:order:create:", expire = 300, message = "请勿重复提交订单")
public Result<OrderDetailVO> createOrder(@Validated @RequestBody OrderCreateDTO dto) { ... }
```

- 一个注解搞定幂等校验，业务代码零侵入
- 支持 Header / SpEL / 自动生成三种 key 策略，按场景灵活选择
- SpEL 表达式直接从方法参数提取业务标识（如 `#id`、`#dto.orderNo`），实现资源级幂等

### 5.2 分级防护——P0/P1/P2 按业务重要性分级

- **P0 资金类**：下单/支付/退款/秒杀，多重保障（注解 + 锁 + 事务 + 唯一索引）
- **P1 状态变更类**：取消/确认/发货/评论/领券，注解 + 状态机校验
- **P2 内部调用类**：Feign 接口防重试，SpEL 提取 orderNo 防重复扣减

### 5.3 下单四重防护——确保资金安全

```
下单流程（四重防护）：
┌─────────────────────────────────────────────────────────────┐
│ 1. @Idempotent 注解（SETNX）—— 防重复提交                    │
│    ↓ Redis 异常降级放行                                      │
│ 2. 分布式锁（order:create:{userId}）—— 防并发下单            │
│    ↓ 锁获取失败抛异常                                        │
│ 3. 数据库事务（@Transactional）—— 保证订单+库存一致性        │
│    ↓ 异常回滚                                                │
│ 4. 订单号唯一索引 —— 最终兜底，防止脏数据                    │
└─────────────────────────────────────────────────────────────┘
```

### 5.4 秒杀 Lua 原子操作——防超卖 + 防重复

```
秒杀流程（Lua 原子操作 + MQ 异步）：
┌─────────────────────────────────────────────────────────────┐
│ 1. 幂等锁（idempotent:seckill:grab:{seckillId}:{userId}）5s │
│    ↓ 防止 5 秒内重复点击                                     │
│ 2. Lua 脚本原子操作：查库存 + 扣库存 + 记已购                │
│    ↓ 返回 1=成功, -1=库存不足, -2=超限购                     │
│ 3. 发送 MQ 消息异步创建订单                                  │
│    ↓ MQ 发送失败回退 Redis 库存                              │
│ 4. 消费者创建秒杀订单（order_type=2, seckill_id）            │
│    ↓ 订单超时取消回退 Redis 库存 + 商品库存                  │
└─────────────────────────────────────────────────────────────┘
```

**关键设计**：
- 秒杀幂等锁与库存扣减**分离**：先抢锁（防重复点击），再 Lua 扣库存（防超卖）
- 秒杀是**强依赖** Redis：不降级，Redis 异常直接拒绝（返回"系统繁忙"）
- MQ 发送失败回退库存：保证库存数据一致
- 订单超时取消双回退：同时回退 Redis 秒杀库存和商品库存

### 5.5 降级策略——Redis 异常不阻断业务

| 接口 | Redis 异常时 | 原因 |
|------|--------------|------|
| 下单 | 降级放行 | 幂等是防护，分布式锁+事务+唯一索引兜底 |
| 秒杀 | **拒绝请求** | 超卖比拒绝对业务伤害更大 |
| 支付回调 | 降级放行 | 状态校验+唯一索引兜底 |
| 其他 | 降级放行 | 幂等是防护而非阻断 |

### 5.6 异常回滚——业务失败允许重试

业务方法抛异常时，自动删除 Redis Key 允许客户端重试：
- `BusinessException`（如库存不足、券已过期）→ 删除 Key，用户可修改后重试
- `RuntimeException`（如数据库超时）→ 删除 Key，用户可重试
- 正常返回 → Key 自然过期，防止成功后重试

### 5.7 支付回调四重保障

```
POST /payment/callback
┌─────────────────────────────────────────────────────────────┐
│ 1. @Idempotent 注解（SETNX, key=#dto.paymentNo, TTL 600s）  │
│ 2. 分布式锁（payment:callback:lock:{paymentNo}）            │
│ 3. 状态校验（订单已支付则忽略重复回调）                      │
│ 4. 唯一索引（out_trade_no 唯一约束）                        │
└─────────────────────────────────────────────────────────────┘
```

### 5.8 完整单元测试覆盖

- `IdempotentAspectTest`：18 个测试覆盖 SETNX 成功/失败、键解析优先级、SpEL 解析、Header 解析、异常回滚、Redis 降级、非 SETNX 策略
- `OrderServiceImplTest`：21 个测试覆盖下单全流程，验证重构后功能一致

## 六、前端配合方案

### 6.1 两种策略的前端差异

| 策略 | 后端注解 | 前端行为 | 幂等键来源 |
|------|----------|----------|------------|
| **Header 策略** | `@Idempotent(prefix="...")` 无 `key` 属性 | 前端生成 `X-Idempotent-Key` 注入 Header | 前端生成 |
| **SpEL 策略** | `@Idempotent(key="#id", prefix="...")` | 前端**不传** Header，后端从参数提取 | 业务参数 |

> **关键**：Header 优先级最高。如果前端对 SpEL 策略接口传了 Header，会覆盖 SpEL 键，
> 导致每次请求 key 不同（随机值），失去资源级幂等效果。

### 6.2 前端白名单注入方案

前端 `request.ts` 请求拦截器中，仅对 **Header 策略接口** 注入 `X-Idempotent-Key`：

```typescript
// Header 策略接口白名单（仅这些接口需要前端传幂等键）
const IDEMPOTENT_HEADER_URLS = [
  { method: 'post', pattern: /^\/order$/ },              // 创建订单
  { method: 'post', pattern: /^\/payment\/create/ },     // 创建支付
  { method: 'post', pattern: /^\/product\/comment$/ },   // 创建评价
]
```

**白名单外的 POST/PUT/PATCH 请求不注入 Header**，由后端 SpEL 策略或状态机保障幂等。

### 6.3 幂等键生成规则

```
格式：{业务类型}_{用户标识}_{时间戳}_{随机串}
示例：order_a1b2c3d4_1700000000000_abc12345
```

- **业务类型**：order/payment/comment，方便日志分类
- **用户标识**：token 前 8 位，用户级隔离
- **时间戳 + 随机串**：保证唯一性

### 6.4 错误码 10007 处理

后端重复请求返回 `code=10007`，前端错误码映射表增加：

```typescript
10007: '请勿重复操作，请稍后再试',
```
