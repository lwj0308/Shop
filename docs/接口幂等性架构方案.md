# Shop 项目接口幂等性架构方案

> 基于电商高并发幂等性面试考点设计，构建"注解化 + 分级防护"的统一幂等体系
> 生成时间：2026-07-08

---

## 一、背景与目标

### 1.1 为什么需要接口幂等性？

电商系统的写操作（下单、支付、退款等）面临三类重复请求风险：

| 风险场景 | 触发原因 | 业务后果 |
|----------|----------|----------|
| 用户重复点击 | 网络卡顿、按钮没禁用 | 重复下单、重复扣款 |
| 网络重试 | 超时后客户端自动重试、Feign 重试 | 重复扣库存、重复核销券 |
| 回调重发 | 第三方支付平台重复回调 | 重复更新订单状态、重复发货 |
| MQ 重复消费 | RocketMQ At-Least-Once 语义 | 重复创建秒杀订单 |

**核心目标**：保证同一业务请求无论被提交多少次，业务结果只有一个。

### 1.2 当前实现现状

| 接口 | 实现方式 | Key 前缀 | TTL | 问题 |
|------|----------|----------|-----|------|
| 下单 `POST /order` | 手写 SETNX | `order:idempotent:` | 300s | 未复用 @Idempotent 注解 |
| 秒杀抢购 `POST /seckill/grab` | 手写 SETNX | `seckill:grab:lock:` | 5s | 与库存扣减原子绑定，合理 |
| 支付回调 `POST /payment/callback` | 分布式锁+状态+唯一索引 | `payment:callback:lock:` | - | 三重保障，但未统一规范 |
| 支付创建 `POST /payment/create` | ❌ 未实现 | - | - | 可能重复创建支付单 |
| 取消订单 `PUT /order/{id}/cancel` | ❌ 未实现 | - | - | 可能重复取消 |
| 退款 `POST /payment/refund` | ❌ 未实现 | - | - | 可能重复退款 |
| 评论创建 `POST /product/comment/create` | ❌ 未实现 | - | - | 可能重复评论 |
| 领券 `POST /coupon/receive` | ❌ 未实现 | - | - | 可能重复领券 |
| 库存扣减（Feign） | ❌ 未实现 | - | - | 重试导致重复扣减 |

**已有基础设施**：
- `@Idempotent` 注解（shop-common）：功能完整，支持 Header/SpEL/自动生成三种 key 策略
- `IdempotentAspect` 切面：SETNX 原子 Lua 脚本 + 降级放行 + 异常回滚，有完整单元测试
- 前端 `request.ts`：已自动为 POST/PUT/PATCH 请求注入 `X-Idempotent-Key` header
- `ErrorCode.REPEAT_REQUEST`（10007）：错误码已定义

**核心问题**：`@Idempotent` 注解功能完整但**零使用**，三个接口各写各的，其余接口无防护。

### 1.3 升级目标

从"零散手写 + 大量缺失"升级为"注解化统一 + 分级防护"，实现 **一次开发、处处复用**。

## 二、幂等性原理与策略（面试高频考点）

### 2.1 四种主流幂等方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| **SETNX** | Redis SETNX 占用 key，重复请求拒绝 | 实现简单、性能高、通用 | 需要选 key、TTL | 大多数写接口 |
| **Token 令牌** | 前端先获取 Token，提交时验证并删除 | 安全性高、无 TTL 困扰 | 需要额外接口、时序依赖强 | 表单提交、敏感操作 |
| **状态机** | 依赖数据库状态字段判断是否已处理 | 强一致、无需 Redis | 仅适合有状态的业务 | 订单状态、支付状态 |
| **唯一索引** | 数据库唯一约束兜底 | 最终一致、防重绝对 | 只能兜底、报错处理复杂 | 回调日志、订单号 |

### 2.2 本项目选型策略

```
对外接口（用户端）：
  @Idempotent 注解（SETNX 策略）+ Header（X-Idempotent-Key）
  适用：下单、支付创建、退款、取消订单、确认收货、评论、领券

内部接口（Feign）：
  @Idempotent 注解（SETNX 策略）+ SpEL（业务参数提取 key）
  适用：库存扣减、券核销、销量累加

特殊场景（秒杀）：
  保留手写 Lua 脚本（库存扣减与幂等原子绑定，无法拆分）
  原因：秒杀的"防重复点击"和"扣库存"必须原子执行，否则会超卖

最终兜底：
  数据库唯一索引 + 状态机校验
  适用：支付回调（out_trade_no 唯一索引 + 支付状态校验）
```

### 2.3 幂等键解析优先级（@Idempotent 注解）

```
1. Header（X-Idempotent-Key）：对外接口优先，前端自动生成
       ↓ 为空时回退
2. SpEL 表达式：内部接口优先，从业务参数提取（如 #dto.orderNo）
       ↓ 为空时回退
3. 自动生成：className.methodName:userId:argsHash
       兜底策略，确保总有 key
```

## 三、幂等性分级设计

### 3.1 分级标准

| 级别 | 含义 | 降级策略 | 适用接口 |
|------|------|----------|----------|
| **P0** | 资金类，必须幂等 | Redis 异常时**降级放行**（幂等是防护） | 下单、支付、退款、秒杀 |
| **P1** | 状态变更类，建议幂等 | Redis 异常时降级放行 | 取消、确认、发货、评论、领券 |
| **P2** | 内部调用类，防重调用 | Redis 异常时降级放行 | 库存扣减、券核销 |
| **P3** | 不需要幂等 | - | 查询、统计、列表 |

> **注意**：秒杀是例外。秒杀的 Redis 库存是**强依赖**（超卖比拒绝对业务伤害更大），不能降级放行。

### 3.2 接口清单与幂等策略

#### P0 资金类（必须幂等）

| 模块 | 接口 | 方法 | 幂等键来源 | Key 前缀 | TTL | 备注 |
|------|------|------|------------|----------|-----|------|
| order | `POST /order` 创建订单 | Header | X-Idempotent-Key | `idempotent:order:create:` | 300s | 重构：移除手写逻辑 |
| payment | `POST /payment/create` 创建支付 | Header | X-Idempotent-Key | `idempotent:payment:create:` | 300s | 新增 |
| payment | `POST /payment/callback` 支付回调 | SpEL | #dto.paymentNo | `idempotent:payment:callback:` | 600s | 新增注解，保留三重保障 |
| payment | `POST /payment/refund` 退款 | SpEL | #paymentId | `idempotent:payment:refund:` | 300s | 新增 |
| order | `POST /seckill/grab` 秒杀抢购 | 手写 | seckillId+userId | `idempotent:seckill:grab:` | 5s | 保留手写（原子绑定） |

#### P1 状态变更类（建议幂等）

| 模块 | 接口 | 方法 | 幂等键来源 | Key 前缀 | TTL | 备注 |

## 四、Redis Key 规范

### 4.1 命名规范

```
格式：idempotent:{服务名}:{业务标识}:{幂等键}
```

**示例**：
```
idempotent:order:create:order_1001_1700000000000_abc123
idempotent:payment:callback:PAY202607080001
idempotent:product:deduct:ORD202607080001
idempotent:seckill:grab:10086_1001
```

### 4.2 TTL 策略

| 业务类型 | TTL | 原因 |
|----------|-----|------|
| 下单 | 300s（5分钟） | 覆盖订单创建全流程，防止超时重试 |
| 支付创建 | 300s | 防止重复创建支付单 |
| 支付回调 | 600s（10分钟） | 第三方可能延迟重发回调 |
| 退款 | 300s | 防止重复退款 |
| 秒杀抢购 | 5s | 短时防重复点击，不影响二次抢购 |
| 状态变更 | 60s | 短时防误操作 |
| 内部调用 | 300s | 覆盖 Feign 重试窗口 |

### 4.3 异常回滚策略

| 场景 | 处理方式 | 原因 |
|------|----------|------|
| 业务方法正常返回 | Key 自然过期 | 不删除，防止成功后重试 |
| 业务方法抛 BusinessException | 删除 Key，允许重试 | 业务失败应允许重试 |
| 业务方法抛其他异常 | 删除 Key，允许重试 | 系统异常应允许重试 |
| Redis SETNX 异常 | 降级放行 | 幂等是防护，不阻断业务 |
| Redis 删除 Key 异常 | 仅记录日志 | 不影响主流程 |

## 五、高可用保障设计（下单/秒杀专项）

> 用户特别要求：务必保证下单和秒杀的功能高可靠、高可用

### 5.1 下单接口高可用保障

```
下单流程（四重防护）：
┌─────────────────────────────────────────────────────────────┐
│ 1. @Idempotent 注解（SETNX）—— 防重复提交                    │
│    ↓ Redis 异常降级放行                                      │
│ 2. 分布式锁（order:create:{userId}）—— 防并发下单            │
│    ↓ 锁获取失败抛异常                                        │
│ 3. 数据库事务（@Transactional）—— 保证订单+库存一致性        │
│    ↓ 异常回滚                                                │
│ 4. 订单号唯一索引 —— 最终兜底，防止脏数据                    │
└─────────────────────────────────────────────────────────────┘
```

**关键设计**：
- 幂等 Key 在事务外校验：避免事务回滚后 Key 已消耗
- 分布式锁在幂等后、事务前：防止并发下单
- 库存扣减走 Feign 批量接口：减少网络调用
- 超时延时消息：30分钟自动取消未支付订单

### 5.2 秒杀接口高可用保障

```
秒杀流程（Lua 原子操作 + MQ 异步）：
┌─────────────────────────────────────────────────────────────┐
│ 1. 幂等锁（seckill:grab:lock:{seckillId}:{userId}）5s TTL  │
│    ↓ 防止 5 秒内重复点击                                     │
│ 2. Lua 脚本原子操作：查库存 + 扣库存 + 记已购                │
│    ↓ 返回 1=成功, -1=库存不足, -2=超限购                     │
│ 3. 发送 MQ 消息异步创建订单                                  │
│    ↓ MQ 发送失败回退 Redis 库存                              │
│ 4. 消费者创建秒杀订单（order_type=2, seckill_id）            │
│    ↓ 订单超时取消回退 Redis 库存 + 商品库存                  │
└─────────────────────────────────────────────────────────────┘
```

**关键设计**：
- 秒杀幂等锁与库存扣减**分离**：先抢锁（防重复点击），再 Lua 扣库存（防超卖）
- 秒杀是**强依赖** Redis：不降级，Redis 异常直接拒绝（返回"系统繁忙"）
- MQ 发送失败回退库存：保证库存数据一致
- 订单超时取消双回退：同时回退 Redis 秒杀库存和商品库存

### 5.3 降级策略对比

| 接口 | Redis 异常时 | 原因 |
|------|--------------|------|
| 下单 | 降级放行 | 幂等是防护，分布式锁+事务+唯一索引兜底 |
| 秒杀 | **拒绝请求** | 超卖比拒绝对业务伤害更大 |
| 支付回调 | 降级放行 | 状态校验+唯一索引兜底 |
| 其他 | 降级放行 | 幂等是防护而非阻断 |

## 六、重构与开发计划

### 6.1 重构现有接口

| 接口 | 改动内容 | 风险 |
|------|----------|------|
| 下单 `OrderController.createOrder` | 移除 `@RequestHeader X-Idempotent-Key` 参数和 `checkIdempotentToken`，改用 `@Idempotent` 注解 | 低：注解逻辑与手写一致 |
| 秒杀 `SeckillServiceImpl.executeSeckill` | 统一 key 前缀为 `idempotent:seckill:grab:`，保留手写 Lua 逻辑 | 极低：仅改前缀 |
| 支付回调 `PaymentController.handleCallback` | 增加 `@Idempotent` 注解（SpEL模式），保留原有三重保障 | 低：注解在前，原有逻辑兜底 |

### 6.2 新增幂等接口

按优先级分三批实施：

**第一批（P0 资金类）**：
- 支付创建 `PaymentController.createPayment` —— `@Idempotent(prefix="idempotent:payment:create:")`
- 退款 `PaymentController.refund` —— `@Idempotent(key="#paymentId", prefix="idempotent:payment:refund:")`

**第二批（P1 状态变更类）**：
- 取消订单 `OrderController.cancelOrder` —— `@Idempotent(key="#id", prefix="idempotent:order:cancel:")`
- 确认收货 `OrderController.confirmReceive` —— `@Idempotent(key="#id", prefix="idempotent:order:confirm:")`
- 发货 `OrderController.adminDeliverOrder` —— `@Idempotent(key="#id", prefix="idempotent:order:deliver:")`
- 创建评论 `CommentController.createComment` —— `@Idempotent(prefix="idempotent:product:comment:")`
- 领取优惠券 `UserCouponController.receiveCoupon` —— `@Idempotent(key="#couponId", prefix="idempotent:coupon:receive:")`

**第三批（P2 内部调用类）**：
- 批量扣库存 `ProductInnerController.batchDeductStock` —— `@Idempotent(key="#dto.orderNo", prefix="idempotent:product:deduct:")`
- 批量回滚库存 `ProductInnerController.batchRollbackStock` —— `@Idempotent(key="#dto.orderNo", prefix="idempotent:product:rollback:")`
- 核销优惠券 `UserCouponController.useCoupon` —— `@Idempotent(key="#dto.orderNo", prefix="idempotent:coupon:use:")`
- 回退优惠券 `UserCouponController.rollbackCoupon` —— `@Idempotent(key="#dto.orderNo", prefix="idempotent:coupon:rollback:")`

### 6.3 确保各服务能扫描到 @Idempotent 注解

`IdempotentAspect` 位于 `shop-common` 模块，需要确保各业务服务的 `@ComponentScan` 能扫描到 `com.shop.common.annotation` 包。

**检查方式**：
- 各服务 Application 类的 `@SpringBootApplication` 默认扫描 `com.shop.{服务名}` 包
- 需要增加 `@ComponentScan(basePackages = {"com.shop.order", "com.shop.common"})` 或类似配置
- 或者确认 `shop-common` 已被各服务依赖（pom.xml）
